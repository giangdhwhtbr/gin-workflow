The Agentic Development Lifecycle

From requirement to merge through recorded quality gates

discuss → plan → orchestrate → execute → ship

Navigation: Press ← / → or PageUp / PageDown or Space to navigate slides, Home / End to jump.

Why an Agentic Lifecycle

Agents need gates, evidence, and a bounded scope

Hard Phase Boundaries

Agents need gates, evidence, and a bounded scope. Stages enforce strict stops: one stage invocation executes exactly one stage and exits.

Evidence Over Assertion

An agent claiming "tests pass" or "feature complete" is never enough. Every claim requires machine-verifiable proof: command output with zero failures, verified diffs, and clean test baselines.

Human Control at Gates

The agent does the heavy lifting, but people maintain authority: confirming the design spec, approving the plan decomposition, and authorizing every merge, pull request, or discard.

Core principle: Mechanical checks run in git hooks at zero token cost; human judgment decides scope, architecture, and integration.

The Lifecycle at a Glance

Swim lanes across stages, gates, people, agents, and automation

discuss → requirement_confirmed

Clarify intent before touching any code or plan

What the Agent Does

  • Runs /discuss <requirement> to explore existing architecture.
  • Asks clarifying questions one at a time, bounded by clarify.max_questions (default 8).
  • Proposes concrete architectural approaches with trade-offs.
  • Writes the confirmed design specification to .planning/specs/<date>-<topic>-design.md.

Human Confirmation & Gate

  • The agent pauses and waits for your confirmation.
  • You confirm the chosen design and accepted scope.
  • Gate recorded: requirement_confirmed via gin-workflow record requirement-confirmed --evidence <spec> --actor <id>.
  • The stage stops immediately. It never advances to planning automatically.
Process waiver: requirement_confirmed may be waived by the agent with a stated reason.

plan → plan_approved

Structured decomposition into verifiable, test-first tracks

Track Decomposition

  • Runs /plan <topic> from the confirmed design spec.
  • Produces .planning/plans/<date>-<feature>.md with independent tracks.
  • Defines file scope, public interfaces, acceptance criteria, and test-first steps.
  • Assigns portable provider role (e.g. frontend, backend) and reasoning tier (low, medium, high).

Human Gate & Approval

  • Tracks with a Human gate: field mark required manual intervention (credentials, production access, third-party approval).
  • Unattended runs automatically stop before human-gate tracks.
  • You review the strategy and approve the plan.
  • Gate recorded: plan_approved via record plan-approved --evidence <plan> --actor <id>.
Portable planning: Plans never contain concrete model names, vendor IDs, or machine paths. Those are resolved locally during orchestration.

orchestrate → orchestration_ready

Instantiate durable tasks, workspace isolation, and execution routes

Task Hierarchy

Creates a Parent Bead (epic) representing the deliverable, and one Track Bead per plan track with technical acceptance criteria.

Worktree Isolation

Creates an isolated git worktree for the feature, verifying clean test baselines before implementation begins.

Route Resolution

Maps portable track roles and tiers to local provider execution configs, and prints the unattended /goal command.

Gate recorded: orchestration_ready via record orchestration-ready --epic <epic> --evidence <ids; worktree; branch> --actor <id>.

Standalone beads can skip discuss and plan: record the bead directly as its own epic with description and acceptance criteria standing in for spec and plan.

execute → implementation_complete

Test-first implementation and independent review per track

Execution Flow

  • Pick ready track: gin-workflow task ready and claim it.
  • Run gin-workflow rules --files <scope> and apply active rule packs.
  • Write failing test first, run it (red), implement solution, re-run test (green).
  • Keep command execution output as verifiable evidence.

Track Closure & Derived Gate

  • Conduct independent code review in the review ledger.
  • Collect AI usage summary: gin-workflow usage collect --bead <id>.
  • Close track bead: unblocks dependent downstream tracks immediately.
  • Gate derived: implementation_complete is satisfied when every child track of the epic is closed.
Not waivable: implementation_complete is a derived fact, not a formality. It cannot be bypassed with a waiver.

Independent Review & the Review Ledger

Bounded review cycles; the review ledger is recorded by commands and never hand-edited

Review Rules

  • Review runs inside execute per track; it is not a router stage.
  • Session or provider independence: fresh session or routed worker; self-review in the same session is forbidden.
  • Review ledger stored in .planning/reviews/<bead>/ (review.json and review.md).
  • Tracks reviewed snapshot on refs/gin/review/<bead>. Commits after review invalidate approval.
  • Bounded at routing.review.max_cycles. Findings must reach terminal statuses: verified, withdrawn, accepted-as-is, deferred-verified, human-waived.

Evidence Over Self-Assessment

No self-certification: every claim demands observable verification

Claim Requires Not enough
Tests pass test output with 0 failures an earlier run
Bug fixed the original symptom's test passes, red then green code changed
Agent completed the diff checked the agent says so
Requirements met the checklist checked tests passing
Waiting for PR merge a pushed branch and a real PR link uncommitted code
Handoff rule: Agents must report what changed, what was validated, what was waived with reasons, bead statuses, remaining risks, and next commands.

Quality Gates in Git Hooks by Rigor

Zero-token automated verification runs directly in your git workflow

Hooks Architecture

  • pre-commit: Runs lint and typecheck from verify.checks.
  • pre-push: Runs test, plus build at standard rigor and e2e at strict rigor. Stops on first failure.
  • CI: The backstop for large projects: nothing in ship proves a hook ran.

Rigor Presets

Rigor Worktree Review Ledger /quick
easy never self check no allowed
standard parallel independent no allowed
strict always independent yes needs waiver
ship verifies that ledger validation exits cleanly and no code was touched after the latest approval.

ship → shipped

Four explicit integration options; nothing merges without you

Pre-Ship Verifications

  • Requires derived implementation_complete gate.
  • Validates review ledgers in history (--in-history).
  • Nothing but spec and review artifacts changed after the newest approval.
  • In SDD mode: runs specs lint and specs trace.

The Four Integration Choices

  1. Merge locally: merges feature branch into base.
  2. Push & open PR: pushes branch and presents PR link.
  3. Keep branch: preserves worktree and branch for later.
  4. Discard: removes branch and worktree (typed confirmation).
Explicit Human Approval: Merging locally, opening a pull request, or force-pushing each require explicit human authorization before execution.
Gate derived: shipped is recorded upon closing the epic after merge, followed by worktree and review ledger cleanup.

Worktree Isolation & Task Tracking

Clean working directories and durable state ownership

Worktree Isolation

  • Prevents agents from dirtying your primary working directory or index.
  • Harness native tool preferred first; falls back to git worktrees under .planning/worktrees/<track>.
  • Detects existing worktrees: never nests worktree inside worktree.
  • Verifies project test baseline before beginning changes.
  • Worktree paths and branch names are disposable runtime metadata.

Task Tracking Ownership

  • gin-workflow task owns status, priority, assignments, claims, blockers, and dependencies.
  • Markdown backend by default (.planning/tasks/): git-ignored and local to this machine, needs no bd.
  • Beads (bd) backend: durable task graph, cross-repo dependency tracking.
  • All commands query tasks to discover ready work (gin-workflow task ready).

Knowledge Capture & Rule Packs

Accumulating project context and enforcing engineering standards

Durable Project Knowledge

  • Captured during execute in .planning/knowledge/<topic>.md.
  • Stores reusable insights: compatibility constraints, counterintuitive APIs, environment limits, architecture decisions.
  • Never stores transient session thoughts or routine code steps.
  • Reconciled during ship before closing beads.

Automated Rule Packs

  • Injected into agent context based on files in scope (gin-workflow rules --files <scope>).
  • Core packs: core (boundaries, error handling, validation) and lean (reuse first, no speculative code, minimal diff).
  • Language and framework packs: typescript, python, react, nextjs, fastapi, node-api.
  • Review grades findings by rule impact (critical, high, medium).

Variations: /quick, SDD & Team Mode

Adaptable to small fixes, living specifications, or multi-member teams

The Quick Path (/quick)

Fast-track for small, low-risk changes (up to 5 files in one module). Skips specs, plans, and beads. Runs rigor verification and review. Never auto-commits.

SDD Living Specs

The SDD layout keeps living specs in docs/specs/ and proposed changes in docs/changes/, with numbered requirements (REQ-<CAP>-<NNN>) that tests and beads point to.

Team Mode

Opt-in collaboration with member roles, code ownership areas, and gates proven by approved pull requests (e.g. BA confirms spec, Area Lead approves plan, QE approves ship).

Configuration driven: Layout switches via artifacts.layout: sdd; team mode enables via team: in configuration.

Running Unattended

Bounded goal execution, human-gate boundaries, and notifications

Bounded /goal Execution

  • gin-workflow goal --workflow-id <id> prints a goal in dependency order.
  • The goal covers only tracks the agent can finish, leaving out human-gate tracks and their dependents.
  • Allows 6 turns per track up to 30.
  • Prints a No goal: line when no track is left.

Safety Boundaries & Notifications

  • Human Gate: Tracks marked with Human gate: and their dependents are excluded from unattended execution.
  • Notifications: gin-workflow notify --event <event> "<msg>" supports needs_input, run_finished, worker_finished, worker_failed.
  • Notifications are off unless notifications.telegram is true.
  • A message is never approval.
