Why gin-workflow

Four problems every legacy modernization hits

Unclear requirements

Work starts from a chat message. gin-workflow starts from a confirmed spec with user stories and requirement IDs.

Unreviewed AI code

Every track gets an independent review in a clean session before its bead closes.

Lost traceability

Story, requirement, test case, and test stay linked, and stale cases are flagged when a requirement changes.

Invisible cost

Token usage and cost are collected per bead and reported per epic or per sprint.

Lifecycle at a glance

One path from survey to shipped

Amber diamonds are approval gates. The roadmap is the first planning step for a brownfield project: it reads the whole tech-doc set before any epic is planned.

What you get

Seven advantages, each with a mechanism

Evidence-backed gates

A stage ends only when its gate is recorded with evidence: a spec, a plan, command output.

Role-based PR approvals

team.approvals names who approves each gate. The pull request author cannot approve their own gate.

Story to test traceability

Story, REQ: ID, test case with requirement hash, then the test itself.

Isolated worktrees

Each epic gets its own worktree and branch, so parallel work never collides.

Independent review

A reviewer in a separate session records findings in a ledger; the track closes after approval.

Sprint reports

report --sprint shows cost and quality for the sprint's epics and their tracks.

Overridable templates

Roadmap, epic, user story, and design spec follow your files in .agent-workflow/templates/.

Team map

Who acts at each stage

Roadmap approval comes from pm or be_lead (the role list in team.approvals.roadmap), spec approval from ba or be_lead, plan approval from the area lead, and verification from qe. These names are roles in your team.members.

Role · PM

Turn the survey into a roadmap and sprints

Commands

  • /gin-workflow:roadmap
  • /gin-workflow:progress sprint <name>
  • /gin-workflow:report --sprint <name>

You get

  • .planning/roadmap.md after you confirm it
  • Epics <prefix>-rm-<slug> with dependencies in Beads
  • A sprint:<name> label on chosen epics
/gin-workflow:roadmap Goal: move payments and inventory out of
the monolith within two quarters without downtime.

Gate: the roadmap pull request is approved by a member with the roadmap role, never by its author.

Role · BA

Write specs and user stories on a roadmap epic

Commands

  • /gin-workflow:discuss <epic-id>
  • /gin-workflow:progress

You get

  • The existing epic is reused, no second epic
  • A spec with a ## User Stories section
  • Acceptance criteria and REQ: links per story
/gin-workflow:discuss demo-rm-payments

Gate: requirement_confirmed, recorded with the merged spec pull request.

Role · Tech Lead

Set up the team, then plan and orchestrate

Commands

  • /gin-workflow:setup, /gin-workflow:team-setup
  • /gin-workflow:tech-doc
  • /gin-workflow:plan, /gin-workflow:orchestrate
  • /gin-workflow:ship

You get

  • The team: block, CODEOWNERS, commit hook
  • Tracks per area and owner under the reused epic
  • An isolated worktree and dependencies
/gin-workflow:tech-doc whole repository
/gin-workflow:plan
/gin-workflow:orchestrate

Gate: plan_approved, approved by the area lead on the plan pull request.

Role · Dev

Claim a track and build it test-first

Commands

  • gin-workflow team ready
  • gin-workflow team claim <bead>
  • /gin-workflow:execute

You get

  • One track, tests first, inside its file scope
  • An independent review before the bead closes
  • A pushed feature branch
gin-workflow team ready
gin-workflow team claim demo-rm-payments.1
/gin-workflow:execute

A claim fails if a teammate already holds the track. execute refuses a roadmap epic that has no confirmed spec.

Role · QE

Cases from the spec, E2E from the cases

Commands

  • /gin-qa:cases <capability>
  • /gin-qa:e2e <capability>
  • /gin-workflow:verify

You get

  • qa/cases/<capability>.md, each case tied to a requirement hash
  • Playwright specs and evidence under qa/
  • Stale cases flagged when a requirement changes
/gin-qa:cases payments
/gin-qa:e2e payments

Gate: verification_passed. The QE approves the latest commit; a later push needs a new approval.

A sprint in practice

From roadmap epic to sprint report

Plan the sprint

/gin-workflow:roadmap Label demo-rm-payments
and demo-rm-orders-api for sprint 2026-s1.

Review the sprint

/gin-workflow:progress sprint 2026-s1
/gin-workflow:report --sprint 2026-s1

A sprint is a label, sprint:2026-s1, on epics. Their tracks are included in the report.

Day-one checklist

Your first day on a new brownfield project

  • Tech Lead runs /gin-workflow:setup and /gin-workflow:team-setup; every member runs team-setup as a member.
  • Protect the base branch on the host: pull request, approval, code-owner review.
  • Make sure each approving role has a second holder, because authors cannot approve their own pull request.
  • Tech Lead runs /gin-workflow:tech-doc whole repository; the team reviews it.
  • PM runs /gin-workflow:roadmap with the goal; a second role-holder approves the pull request.
  • PM labels the first sprint's epics with sprint:<name>.
  • BA runs /gin-workflow:discuss <epic-id> for the first epic.
  • Put your formats in .agent-workflow/templates/ and qa/guidelines.md before the first spec.

The full flow with a prompt per role is in docs/starters/brownfield-walkthrough.md.
