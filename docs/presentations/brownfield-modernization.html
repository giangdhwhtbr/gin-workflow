Strategic Context

The Brownfield Dilemma & Modernization Strategy

Replacing legacy systems incrementally without halting ongoing business delivery.

Conventional "Big-Bang" Rewrite (High Risk)

  • Extended Freeze: 6 to 12 months with no customer-facing releases.
  • Implicit Requirements: Undocumented business rules buried in legacy code are missed until production rollout.
  • Unbounded Scope: Delays compound as legacy requirements drift during the rewrite period.
  • Binary Payoff: Complete success or catastrophic failure with zero partial rollback capability.

Incremental SDD Modernization (Controlled Risk)

  • Continuous Delivery: Each sprint ships a working, production-ready vertical slice.
  • Living Contracts: Requirements are codified into docs/specs/ with verifiable scenarios.
  • Strangler Fig Routing: Facade routers direct traffic to modernized capabilities one by one.
  • Regression Protection: Pinned hashes ensure legacy parity before retiring old modules.
Strategic Principle: Avoid multi-month specification phases that yield no working software. Modernization delivers production value in every sprint starting from Sprint 1.

Phase 0: Discovery

Automated Discovery of Legacy Codebases

Extracting architecture and boundary contracts directly from repository evidence.

The Legacy Knowledge Gap

  • Outdated Documentation: Wikis, READMEs, and diagrams lag years behind actual production code.
  • Hidden Dependencies: Implicit database triggers, global variables, and undocumented endpoints.
  • High Investigation Cost: Senior engineers spend weeks reading spaghetti code to map interfaces.

Evidence Extraction via /tech-doc

  • Source of Truth: Scans AST, routing tables, and schemas directly from the checked-out codebase.
  • Structured Documentation: Generates 10 standardized modules under docs/codebase/:
    ARCHITECTURE.md, API.md, STRUCTURE.md, INTEGRATIONS.md, STACK.md.
  • Zero Speculation: All findings cite exact file paths and line ranges.
Outcome: A complete, verifiable baseline of current legacy behavior generated in hours instead of weeks, ready to seed the product roadmap.
Roadmap Governance

Feasible Roadmapping: Early Deliverables from Sprint 1

Addressing leadership concerns on deliverable visibility and team workload allocation.

BOD & PM Concern Addressed

"Will early sprints be spent entirely on writing specifications and infrastructure setup with nothing working to demonstrate to clients?"

Answer: No. We reject horizontal slicing (months of pure specs or pure database migrations) in favor of Thin Vertical Slices.

Vertical Slicing Execution Model

  • Sprint 1 Pilot Slice: Extract a single self-contained capability (e.g. Auth or Payment Webhook).
  • End-to-End Delivery: The slice progresses through all stages: discuss → plan → execute → ship.
  • Working Demo: Client and stakeholders inspect a live, working API/UI at the end of Sprint 1.
  • Repeatable Cadence: Sprints 2+ strangle subsequent modules using the established pipeline.

Quality Gate: Discuss

How AI-Generated Specifications Are Formally Verified

Eliminating hallucinations through deterministic grammar and human PR review gates.

1. Deterministic Grammar

Strict EARS Syntax: Requirements must declare clear conditions using SHALL or MUST statements.

GIVEN / WHEN / THEN: Each requirement requires at least one concrete test scenario.

specs lint fails immediately if syntax or scenarios are missing.

2. Human PR Gate

Pull Request Review: Changes are proposed on spec/<epic> and submitted as a Git Pull Request.

Role-Gated Approval: The requirement-confirmed gate requires human BA approval on GitHub/GitLab.

No code or planning can proceed until the spec PR is merged.

3. Visual Asset Grounding

Multimodal Analysis: BAs save UI screenshots into docs/specs/<cap>/assets/.

The AI Agent reads wireframes to extract input fields, validation rules, and error states directly from images.

Screenshots are linked directly into the markdown specification.

The Human-in-the-Loop Safeguard: The AI Agent proposes and structures requirements; the human Business Analyst retains sole authority to confirm and approve them.
Stages 2 & 3: Plan & Orchestrate

Architectural Decomposition & Workspace Isolation

Enforcing subsystem boundaries and preventing git conflicts during development.

Bounded Tracks in plan.md

  • Subsystem Scoping (Area:): Each track is strictly bound to its assigned directory (e.g. Area: modern_api vs Area: legacy_core).
  • Boundary Protection: Code edits that touch files outside the track's declared area are automatically rejected.
  • Requirement Mapping: Every track explicitly enumerates its target requirements: Requirements: REQ-AUTH-001, REQ-AUTH-002.

Automated Git Worktree Isolation

  • Dedicated Working Directory: /orchestrate creates an isolated Git worktree under .planning/worktrees/ for each track.
  • Zero Git Collisions: Developers and parallel AI subagents build, edit, and test simultaneously without branch locking.
  • Clean Integration: Dependencies between tracks are tracked in Beads; downstream tracks unlock automatically when upstream PRs merge.
Stage 4: Execute

Ensuring Code Strictly Matches Specification

Guaranteed compliance through bidirectional requirement tagging and automated trace audits.

Test-Driven Development (TDD)

Developers claim tracks via gin-workflow team claim <bead>. Implementation code is not accepted without prior failing unit and integration tests tagged with the exact requirement ID.

Automated Gate Audit (specs trace)

Prior to completion, gin-workflow specs trace cross-references every requirement scenario against test source files. Missing tests or untested scenarios immediately block the ship gate.

Verification

Independent Code Review & The Review Ledger

Structured review findings with documented technical resolutions.

Independent Review Process

  • Independent Evaluator: An isolated review agent inspects the track's git diff against architectural rules, test coverage, and security criteria.
  • Durable Ledger: Findings are recorded in .planning/reviews/<bead>/findings.jsonl with specific line numbers and risk ratings.
  • Bounded Cycles: Maximum review iterations are strictly enforced to prevent circular review debates.

The Verification Protocol

Engineers do not passively accept AI findings. Every finding requires technical verification and one of three documented dispositions:

  • Fix: Correct code and test baseline, then re-verify.
  • Dispute: Provide technical reasoning showing current code is correct as designed.
  • Defer: Record a formal issue or signed architectural waiver.

A track cannot close with unaddressed findings in its review ledger.

Quality Engineering

Focused QA: Preventing Test Overwhelm with gin-qa

Content-hash drift detection and targeted Playwright E2E automation.

The AI Test Generation Trap

Unconstrained AI tools generate hundreds of trivial, low-value test cases. QA engineers become overwhelmed triaging noisy test suites, slowing down delivery.

The Fix: Restrict test generation strictly to formal requirements and steer test depth via team guidelines.

The gin-qa Architecture

  • Policy Steering (qa/guidelines.md): QA establishes rules: only critical user journeys receive Type: e2e, while edge cases use unit/integration tests.
  • Hash-Pinned Drift Detection (gin-qa cases plan): Test cases store the SHA hash of their requirement (REQ-AUTH-001@hash).
    The tool categorizes tests into:
    • missing: New requirements needing test cases.
    • stale: Requirements modified since last review.
    • obsolete: Deleted requirements.
  • No Duplicate Work: Unchanged test cases are untouched. QA reviews only modified deltas.
Stage 5: Ship

Safe Integration & Living Spec Archival

Atomic synchronization of living specifications and automated release packaging.

The Ship Stage Gate

  1. Pre-Ship Verification: Runs full test suite, linting, typechecks, and specs trace verification.
  2. Atomic Spec Archival: specs archive merges requirements from spec-delta.md into docs/specs/<cap>/spec.md.
  3. Historical Archival: The change proposal folder moves to docs/changes/archive/ with its full audit trail.
  4. Pull Request Integration: Opens final integration PR for QE approval (team.approvals.ship: [qe]).

Long-Term Architecture Health

  • Always Up-To-Date Living Specs: docs/specs/ remains the perpetual single source of truth for the entire application.
  • Safe Strangling: As modern modules ship, legacy code paths are systematically disabled and cleaned up.
  • No Documentation Debt: Requirements evolve alongside code; regression test suites preserve business logic permanently.
