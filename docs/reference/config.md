# Configuration reference

Installing the plugin never changes a repository. Run `/setup` once per repository; it asks one question at a time, previews the configuration, and writes it only after you approve (see [`gin-workflow setup`](cli.md#gin-workflow-setup)). Lifecycle skills read only the generated effective configuration and stop with setup guidance when it is missing; they never run setup themselves.

## Files

| File | Committed | Contents |
|---|---|---|
| `AGENTS.md` | yes | The block between `<!-- gin-workflow:start … -->` and `<!-- gin-workflow:end -->` is generated by `gin-workflow setup` from this configuration; edit outside it. Deleting it opts out of `refresh`; `setup init --approve` adds it back. `CLAUDE.md` imports it with `@AGENTS.md` |
| `.agent-workflow/config.yaml` | yes | Portable settings: project profile, verify commands, artifact paths, routing roles, model catalog, rules, team, QA. No commands or secrets; model names only in the model catalog |
| `.agent-workflow/orchestrator.local.yaml` | no | Machine-local executables for worker harnesses ([gin-orchestrator](../orchestrator/routing.md)); named `providers.local.yaml` before schema 2.8 |
| `.agent-workflow/generated/effective-config.yaml` | no | The resolved configuration every skill reads |
| `.agent-workflow/generated/config-provenance.yaml` | no | Which layer set each value |
| `.agent-workflow/usage-prices.yaml` | your choice | Model prices for `gin-workflow usage` |
| `.agent-workflow/runtime/` | no | Gate events (`events.jsonl`), assignment manifests, session harness override, evidence |
| `.agent-workflow/backups/` | no | Backups taken before a migration |

On first setup, `setup init` writes `.agent-workflow/.gitignore` with `generated/`, `runtime/`, `backups/`, `orchestrator.local.yaml`, and `providers.local.yaml`, and keeps any lines already in the file. `config.yaml` stays tracked. When gin-orchestrator writes `orchestrator.local.yaml`, it adds that file to `.agent-workflow/.gitignore` in the main checkout. The schema 2.8 migration, when it renames `providers.local.yaml`, adds the same five entries.

Full examples ship with the plugin: `plugins/gin-workflow/src/examples/config.full.yaml` and, in gin-orchestrator, `plugins/gin-orchestrator/src/examples/orchestrator.local.example.yaml`.

## Precedence

Later layers override earlier ones; `config-provenance.yaml` records the winner for each field.

1. Built-in defaults
2. User profile (`GIN_WORKFLOW_USER_PROFILE`, a YAML path)
3. Organization profile (`GIN_WORKFLOW_ORGANIZATION_PROFILE`)
4. `.agent-workflow/config.yaml`
5. `.agent-workflow/harness-override.yaml`
6. `.agent-workflow/local.yaml`
7. Command overrides

Portable layers are validated before anything is written. A command key (such as `command` or `executable`), a concrete model name outside `models.<harness>.models`, or a literal secret is rejected there. Executables belong in `orchestrator.local.yaml`.

## Versions and migration

`schema_version`, `workflow_version`, and `setup_cli_version` are separate compatibility channels; the current value of each is `2.9`. When the installed CLI is newer, `gin-workflow setup update` proposes the registered migration and applies it with `--approve`, after writing a validated backup to `.agent-workflow/backups/`. `rollback --backup PATH` restores one. Migrations change configuration only; they never move plans, Beads data, review ledgers, worktrees, or other artifacts.

In schema 2.8, worker routing configuration (`concurrency`, `queue`, `worker`, `circuit_breaker`, and roles naming worker providers) moves under `orchestrator:`. `gin-workflow setup update --to-version 2.8 --approve` preserves explicit settings, defaults an unset `providers.task_tracking` to `beads`, and renames `providers.local.yaml` to `orchestrator.local.yaml`.

Schema 2.9 replaces `model_tiers` with the [`models`](#models) catalog. `gin-workflow setup update --to-version 2.9` removes `model_tiers` and keeps every other key. For each provider in `orchestrator.local.yaml` that still lists tier `models:` and has no `models` entry yet, it proposes a catalog entry: the tier models in `low`, `medium`, `high` order, without duplicates. Efforts are not carried over; add `efforts` to the entry yourself. With `--approve` it writes those entries to `config.yaml` and removes `models:` from `orchestrator.local.yaml`, keeping `executable`.

A schema 2.9 configuration that sets `model_tiers` is rejected. On an older schema, `gin-workflow setup doctor` reports `model_tiers`, and it reports tier `models:` left in `orchestrator.local.yaml`, which gin-orchestrator refuses to load.

## Keys

### Top level

| Key | Values | Default |
|---|---|---|
| `harness` | `claude`, `codex`, `antigravity`, `opencode`: the main harness that coordinates the workflow | set by setup |
| `provider_mode` | `single` (the main harness does everything) or `multi` (routes and reviews are delegated to [gin-orchestrator](../orchestrator/README.md) when it is installed) | `single` |

### `project`

| Key | Values | Default |
|---|---|---|
| `stage` | `greenfield`, `brownfield`, `legacy` | `brownfield` |
| `shape` | `frontend`, `backend`, `fullstack`, `library`; selects the `references/shape-<shape>.md` appendix the developer reads | `fullstack` |
| `monorepo`, `packages` | monorepo flag and detected packages | `false` |
| `stack_intent` | free text for a greenfield project | `""` |
| `rigor` | `easy`, `standard`, `strict` | `standard` |
| `worktree` | `never`, `parallel`, `always` | from rigor |
| `review` | `self_check`, `independent` | from rigor |
| `review_ledger` | require a review ledger | from rigor |

Rigor presets:

| Rigor | Worktree | Review | Ledger | `/quick` |
|---|---|---|---|---|
| `easy` | never | self check | no | allowed |
| `standard` | for parallel work | independent | no | allowed |
| `strict` | always | independent | yes | needs a `requirement_confirmed` waiver |

### `verify.checks`

`lint`, `typecheck`, `test`, `build`, `e2e`: shell commands. The git hooks ([`gin-workflow hooks`](cli.md#gin-workflow-hooks)) and `/quick` run the ones the rigor requires. Empty commands are skipped. `gin-workflow setup doctor` reports missing ones.

### `quick`

`max_files` (default 5): the largest change `/quick` accepts; it also accepts only one module.

### `clarify`

`max_questions` (default 8): cap on clarifying questions in `/discuss` and `/roadmap`; at the cap the agent proposes splitting the scope into smaller epics or lists the rest as assumptions.

### `notifications`

`telegram` (boolean, optional, default off): one-way Telegram notifications for lifecycle events (`needs_input`, `run_finished`, `worker_finished`, `worker_failed`). Enable with:

```bash
gin-workflow setup configure --set notifications.telegram=true --approve
```

Credentials are read from `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` in the environment. `gin-workflow setup doctor` warns when `notifications.telegram` is enabled but either credential is missing.

### `artifacts`

| Key | Default | Meaning |
|---|---|---|
| `plans` | `.planning/plans` | approved plans |
| `knowledge` | `.planning/knowledge` | durable project knowledge |
| `beads` | `.beads` | Beads database |
| `runtime`, `evidence` | `.agent-workflow/runtime`, `.agent-workflow/runtime/evidence` | runtime state |
| `layout` | `legacy` | `sdd` turns on living specs |
| `specs`, `changes`, `adr`, `codebase` | `docs/specs`, `docs/changes`, `docs/adr`, `docs/codebase` | SDD folders |
| `spec_review` | `chat` | SDD spec review: `chat` or `pr` |
| `test_globs` | `**/test_*.py`, `**/*_test.py`, `**/*.test.*`, `**/*.spec.*`, `tests/**`, `__tests__/**` | globs that identify test files for `specs trace` |

Worktrees always live under `.planning/worktrees`. `gin-workflow setup doctor` asks you to remove an `artifacts.worktrees` key when any configuration layer sets it.

### `routing`

In schema 2.8, `routing` holds single-harness roles (`preferred: [main_harness]`) and review policy. Worker routing configuration belongs under `orchestrator:`.

| Key | Meaning |
|---|---|
| `roles.<role>.preferred` | `[main_harness]` in single-harness mode |
| `review.role`, `require_independent`, `allow_self_review_fallback`, `max_cycles`, `independence` | independent review policy; `independence` is `session` (default; a fresh session of the main harness) or `provider` (a different harness, which needs gin-orchestrator) |

Plans name roles and a model and effort from the main harness's [model catalog](#models), never providers.

### `orchestrator`

A mapping owned by `gin-orchestrator`. `gin-workflow` checks only that it is a mapping and, as in every portable layer, holds no commands, model names, or secrets. Holds worker roles (`roles.<role>.preferred`, `roles.<role>.fallback`, `roles.<role>.by_tier`), `concurrency`, `queue`, `worker`, and `circuit_breaker`.

### `models`

The model catalog. For each harness, `models` lists its models from weakest to strongest and `efforts` lists its efforts from lowest to highest.

```yaml
models:
  claude:
    models: [haiku, sonnet, opus]
    efforts: [low, medium, high, xhigh, max]
```

| Harness | Built-in `models` | Built-in `efforts` |
|---|---|---|
| `claude` | `haiku`, `sonnet`, `opus` | `low`, `medium`, `high`, `xhigh`, `max` |
| `codex` | `gpt-6-astra` | `low`, `medium`, `high`, `xhigh` |
| `antigravity`, `opencode` | `provider_default` (the CLI's own default) | none |

A configured harness entry replaces that harness's built-in entry as a whole. `models` needs at least one entry, and `efforts` may be empty or left out; entries in both lists are unique, non-empty strings. Plan tracks pick their model and effort from the main harness's entry, and `gin-workflow state --format json` prints that entry as `catalog`. gin-orchestrator maps a route into another harness's entry by rank ([rank mapping](../orchestrator/routing.md#rank-mapping)).

### `policy.approval`

`ttl_seconds` (default 86400) and `bind_to_scope` (default `true`): how long a recorded approval stays valid and whether it is tied to the source tree it approved.

### `rules`

| Key | Meaning |
|---|---|
| `packs` | extra rule packs to enable, for example `[typescript, react]` |
| `disabled` | packs to turn off, including the defaults |

`core`, `lean`, and `docs` are always enabled unless disabled; `docs` applies only to Markdown files. Project packs live in `.agent-workflow/rules/`. Inspect the result with `gin-workflow rules --list`. See [Rule packs](../guides/rules.md).

### `providers`

`task_tracking`: `markdown` or `beads`. Unset means `markdown`, or `beads` when `team:` is configured. `markdown` keeps one Markdown file per task under `.planning/tasks/` in the main checkout, git-ignored and local to this machine; it needs no `bd`. Team mode and `gin-workflow usage` require `beads`.

### `team`

Present only in team mode ([guide](../guides/team.md)). Keys: `host` (`github` or `gitlab`), `commit_convention` (`conventional` or `none`), `members` (email → `roles`, `login`), `areas` (name → `paths`, `lead`, `roles`), `approvals`, and `beads_sync.remote`. `approvals` maps a gate (`requirement_confirmed`, `plan_approved`, `ship`, `roadmap`) to a role list. `plan_approved` may be `area_lead` instead, and `roadmap` gates the `/roadmap` pull request.

### `qa`

Used by the `gin-qa` add-on: `cases` (default `qa/cases`), `guidelines` (default `qa/guidelines.md`), `e2e` (default `qa/e2e`).

## `orchestrator.local.yaml`

Read only by gin-orchestrator. It holds one executable per worker harness; models come from the [`models`](#models) catalog. Before schema 2.8 this file was `providers.local.yaml`; `gin-workflow setup update --to-version 2.8 --approve` renames it.

```yaml
schema_version: "2.9"
providers:
  claude:
    executable: claude
  antigravity:
    executable: agy
  opencode:
    executable: opencode
  codex:
    executable: codex
```

gin-orchestrator rejects a provider entry with any key besides `executable`; a `models:` key left from schema 2.8 moves to the catalog with the [2.9 migration](#versions-and-migration). `gin-workflow setup models --provider <name>` lists the models a CLI reports (it needs gin-orchestrator). Credentials stay with each CLI's own login.

## `usage-prices.yaml`

```yaml
prices:
  <model id>: {input: 3.0, output: 15.0, cache_read: 0.3, cache_write: 3.75}
```

Prices are per million tokens; USD is a convention, since the code applies no currency. Models without a price show `-` and are listed as `unpriced`.
