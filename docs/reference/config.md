# Configuration reference

Installing the plugin never changes a repository. Run `/setup` once per repository; it asks one question at a time, previews the configuration, and writes it only after you approve (see [`gin setup`](cli.md#gin-setup)). Lifecycle skills read only the generated effective configuration and stop with setup guidance when it is missing; they never run setup themselves.

## Files

| File | Committed | Contents |
|---|---|---|
| `AGENTS.md` | yes | The block between `<!-- gin:start … -->` and `<!-- gin:end -->` is generated by `gin setup` from this configuration; edit outside it. Deleting it opts out of `refresh`; `setup init --approve` adds it back. `CLAUDE.md` imports it with `@AGENTS.md` |
| `.ginrc` | yes | The minimum gin version the project needs; see [`.ginrc`](#ginrc) |
| `.agent-workflow/config.yaml` | yes | Portable settings: project profile, verify commands, artifact paths, routing roles, model catalog, rules, team, QA. No commands or secrets; model names only in the model catalog |
| `.agent-workflow/executables.local.yaml` | no | Machine-local paths of the external CLIs (`git`, `bd`, `gh`, `glab`, `npm`, `npx`, `gin`, `codegraph`); written by `setup init` and `setup refresh` |
| `.agent-workflow/generated/effective-config.yaml` | no | The resolved configuration every skill reads |
| `.agent-workflow/generated/config-provenance.yaml` | no | Which layer set each value |
| `.agent-workflow/runtime/` | no | Gate events (`events.jsonl`), assignment manifests, session harness override, evidence |
| `.agent-workflow/backups/` | no | Backups taken before a migration |

On first setup, `setup init` writes `.agent-workflow/.gitignore` with `generated/`, `runtime/`, `backups/`, `executables.local.yaml`, and the names of two local files that older versions wrote, and keeps any lines already in the file. `config.yaml` stays tracked.

A full example ships with the plugin: `plugins/gin-workflow/src/examples/config.full.yaml`.

## Precedence

Later layers override earlier ones; `config-provenance.yaml` records the winner for each field.

1. Built-in defaults
2. User profile (`GIN_WORKFLOW_USER_PROFILE`, a YAML path)
3. Organization profile (`GIN_WORKFLOW_ORGANIZATION_PROFILE`)
4. `.agent-workflow/config.yaml`
5. `.agent-workflow/harness-override.yaml`
6. `.agent-workflow/local.yaml`
7. Command overrides

Portable layers are validated before anything is written. A command key (such as `command` or `executable`), a concrete model name outside `models.<harness>.models`, or a literal secret is rejected there. Machine-local executables belong in `executables.local.yaml`.

## Versions and migration

`schema_version`, `workflow_version`, and `setup_cli_version` are separate compatibility channels; the current value of each is `2.11`. When the installed CLI is newer, `gin setup update` proposes the registered migration and applies it with `--approve`, after writing a validated backup to `.agent-workflow/backups/`. `rollback --backup PATH` restores one. Migrations change configuration only; they never move plans, Beads data, review ledgers, worktrees, or other artifacts.

In schema 2.8, `gin setup update --to-version 2.8 --approve` defaults an unset `providers.task_tracking` to `beads`.

Schema 2.9 replaces `model_tiers` with the [`models`](#models) catalog. `gin setup update --to-version 2.9` removes `model_tiers` and keeps every other key. For each provider in `orchestrator.local.yaml` that still lists tier `models:` and has no `models` entry yet, the update writes a catalog entry to `config.yaml`: the tier models in `low`, `medium`, `high` order without duplicates, plus the provider's built-in `efforts` when any tier declared an effort. The 2.11 update makes the same move before it deletes that file. A schema 2.9 configuration that sets `model_tiers` is rejected. On an older schema, `gin setup doctor` reports `model_tiers`. On any schema it reports tier `models:` left in the local file.

Schema 2.10 removes `notifications`: `gin setup update --to-version 2.10` drops the key and keeps every other key. A schema 2.10 configuration that sets `notifications` is rejected. On an older schema, `gin setup doctor` reports `notifications` as ignored since schema 2.10.

Schema 2.11 removes `orchestrator`, `provider_mode`, and `routing.review.independence`: gin runs every stage in the main harness. `gin setup update --to-version 2.11 --approve` drops the three keys and moves each role name found only under `orchestrator.roles` into `routing.roles` as `preferred: [main_harness]`, so a plan that names the role still validates. It also puts `.agent-workflow/orchestrator.local.yaml` in the backup and deletes it, and `rollback --backup PATH` restores it. A schema 2.11 configuration that holds one of the keys is rejected. On an older schema the keys are ignored: `gin state` warns once and `gin setup doctor` lists one action.

### `.ginrc`

`.ginrc` at the project root holds one line: the minimum gin release version `X.Y.Z` the project needs. It is tracked in git. In a workspace only the parent has one; children and worktrees find it in a parent directory. Any other content, or a file that is not UTF-8, is an error; a UTF-8 byte order mark is allowed.

`gin` looks for the file from the working directory, or `--repository`, upwards. Inside your home directory the search stops below it, so a `.ginrc` in the home directory or above pins nothing there. Outside the home directory it continues to the filesystem root. Worktrees that `gin worktree` creates lie under the parent, so they find its `.ginrc`. A worktree you create by hand outside the parent's tree does not.

`gin` compares its own version with the file before it reads the configuration:

| Installed version | Result |
|---|---|
| Same major version, equal or newer | Compatible |
| Older | Refused: update gin |
| Newer major version | Refused: upgrade the project with `gin setup update --approve`; `gin setup` still runs |
| No `.ginrc` | No check |

`gin setup init --approve` writes the file with the installed version. `gin setup update` proposes raising a missing or lower pin to the installed version and writes it with `--approve`. `gin setup doctor` reports a project without one, and a pin of an older major version. The [CLI reference](cli.md#gin-version) gives the messages and `gin version`. A gin older than 3.1.0 does not read `.ginrc`.

## Keys

### Top level

| Key | Values | Default |
|---|---|---|
| `harness` | `claude`, `codex`, `antigravity`, `opencode`, `copilot`: the main harness that coordinates the workflow | set by setup |

### `project`

| Key | Values | Default |
|---|---|---|
| `stage` | `greenfield`, `brownfield`, `legacy` | `brownfield` |
| `shape` | `frontend`, `backend`, `fullstack`, `library`; selects the `references/shape-<shape>.md` appendix the developer reads | `fullstack` |
| `monorepo`, `packages` | monorepo flag and detected packages; for several repositories under one parent see [`workspace`](#workspace) | `false` |
| `stack_intent` | free text for a greenfield project | `""` |
| `rigor` | `easy`, `standard`, `strict` | `standard` |
| `worktree` | `never`, `parallel`, `always` | from rigor |
| `review` | `self_check`, `independent` | from rigor |
| `review_ledger` | require a review ledger | from rigor |

The resolved `run_at` (from [`verify.run_at`](#verifyrun_at)) also appears under `project` in `gin state --format json`.

Rigor presets:

| Rigor | Worktree | Review | Ledger | `/quick` |
|---|---|---|---|---|
| `easy` | never | self check | no | allowed |
| `standard` | for parallel work | independent | no | allowed |
| `strict` | always | independent | yes | needs a `requirement_confirmed` waiver |

### `verify.run_at`

Where the full suite (`test`, `build`, `e2e`) runs: `track` after each track, `push` once before the push, `host` never locally because the host CI runs it. Optional; the default is `push` under `easy` and `standard` and `track` under `strict`. Any other value is a configuration error. With `host`, `gin hooks run pre-push` and `gin evidence run` run nothing and record nothing, and `gin quick-check` lists only `lint` and `typecheck`. The `pre-commit` hook is unchanged. A workspace child uses the parent's value.

### `verify.checks`

`lint`, `typecheck`, `test`, `build`, `e2e`: shell commands. The git hooks ([`gin hooks`](cli.md#gin-hooks)) and `/quick` run the ones the rigor requires. Empty commands are skipped. `gin setup doctor` reports missing ones. A `project.packages` entry may carry its own `verify.checks`; the git hooks run them only for the packages a change touches, as [`gin hooks run`](cli.md#gin-hooks) describes.

### `quick`

`max_files` (default 5): the largest change `/quick` accepts; it also accepts only one module.

### `clarify`

`max_questions` (default 8): cap on clarifying questions in `/discuss` and `/roadmap`; at the cap the agent proposes splitting the scope into smaller epics or lists the rest as assumptions.

### `usage`

`usage:` is ignored since gin 3.4.0; delete it. gin no longer tracks AI usage.

### `artifacts`

| Key | Default | Meaning |
|---|---|---|
| `plans` | `.planning/plans` | approved plans |
| `knowledge` | `.planning/knowledge` | durable project knowledge |
| `beads` | `.beads` | Beads database |
| `runtime`, `evidence` | `.agent-workflow/runtime`, `.agent-workflow/runtime/evidence` | runtime state |
| `layout` | `legacy` | `sdd` turns on living specs |
| `specs`, `changes`, `adr`, `codebase` | `docs/specs`, `docs/changes`, `docs/adr`, `docs/codebase` | SDD folders |
| `explain` | `.agent-workflow/runtime/explain` | folder for `specs explain` pages: `<explain>/<name>/<name>.html`, and `<explain>/legacy/<app>/<cap>/<cap>.html` with `--legacy` |
| `spec_review` | `chat` | SDD spec review: `chat` or `pr` |
| `test_globs` | `**/test_*.py`, `**/*_test.py`, `**/*.test.*`, `**/*.spec.*`, `tests/**`, `__tests__/**` | globs that identify test files for `specs trace` |

Worktrees always live under `.planning/worktrees`. `gin setup doctor` asks you to remove an `artifacts.worktrees` key when any configuration layer sets it.

### `routing`

`routing` holds roles that resolve to the main harness (`preferred: [main_harness]`) and the review policy.

| Key | Meaning |
|---|---|
| `roles.<role>.preferred` | `[main_harness]` |
| `review.role`, `require_independent`, `allow_self_review_fallback`, `max_cycles` | independent review policy; the reviewer is a fresh session or subagent of the main harness |

Plans name roles and a model and effort from the main harness's [model catalog](#models), never providers.

### `models`

The model catalog. For each harness, `models` lists its models from weakest to strongest and `efforts` lists its efforts from lowest to highest.

```yaml
models:
  claude:
    models: [haiku, sonnet, opus]
    efforts: [low, medium, high, xhigh, max]
```

| Harness | Built-in `models` | Built-in `efforts` |
|---|---|---|
| `claude` | `haiku`, `sonnet`, `opus` | `low`, `medium`, `high`, `xhigh`, `max` |
| `codex` | `gpt-6-astra` | `low`, `medium`, `high`, `xhigh` |
| `antigravity`, `opencode`, `copilot` | `provider_default` (the CLI's own default) | none |

A configured harness entry replaces that harness's built-in entry as a whole. `models` needs at least one entry, and `efforts` may be empty or left out; entries in both lists are unique, non-empty strings. Plan tracks pick their model and effort from the main harness's entry, and `gin state --format json` prints that entry as `catalog`.

### `policy.approval`

`ttl_seconds` (default 86400) and `bind_to_scope` (default `true`): how long a recorded approval stays valid and whether it is tied to the source tree it approved.

### `rules`

| Key | Meaning |
|---|---|
| `packs` | extra rule packs to enable, for example `[typescript, react]` |
| `disabled` | packs to turn off, including the defaults |

`core`, `lean`, and `docs` are always enabled unless disabled; `docs` applies only to Markdown files. Project packs live in `.agent-workflow/rules/`. Inspect the result with `gin rules --list`. See [Rule packs](../guides/rules.md).

### `providers`

`task_tracking`: `markdown` or `beads`. Unset means `markdown`, or `beads` when `team:` is configured. `markdown` keeps one Markdown file per task under `.planning/tasks/` in the main checkout, git-ignored and local to this machine; it needs no `bd`. Team mode requires `beads`.

### `team`

Present only in team mode ([guide](../guides/team.md)). Keys: `host` (`github`, `gitlab`, `gitea`, or `codecommit`), `commit_convention` (`conventional` or `none`), `members` (email → `roles`, `login`, `aws_identity`), `areas` (name → `paths`, `lead`, `roles`), `approvals`, and `beads_sync.remote`. `approvals` maps a gate (`requirement_confirmed`, `plan_approved`, `ship`, `roadmap`) to a policy. A policy is a role list (one listed role must approve), an object `{all: [roles], any: [roles]}` (each `all` role and one `any` role must approve; needs gin-workflow 3.1 or later, and older versions reject the config), or `area_lead` for `plan_approved`. `requirement_confirmed` also takes a map `{capability: <policy>, technical: <policy>, parity: <policy>}` with `capability` required and no other key; a missing kind uses `capability` ([per-kind policies](../guides/team.md#policy-per-epic-kind)). The map form needs gin-workflow 3.1 or later, and older versions reject the config at schema validation. A policy may also be `host`, for any gate and for each kind in the map. Then gin keeps the repository, merge, changed-file, and `check-plan` checks, and checks no approver, author, or head commit. The host's branch protection must then enforce approvals. A `host` gate has no approver roles: any member may waive it where the gate is waivable (`requirement_confirmed`, `plan_approved`), and CODEOWNERS names no spec approver for it. Versions of gin-workflow that predate `host` reject it at schema validation. When the pull request author is the only holder of an `all` role, that role is skipped with a note when the policy has an `any` role, which must still approve; without one, the check refuses. A sole-holder area lead is skipped when the lead of another area approved. `roadmap` gates the `/roadmap` pull request. `permissions.milestone` lists the roles allowed to run `gin milestone` writes; unset means any member. Every listed role must be held by a member. `aws_identity` is the IAM user name, or `<role>/<session>` for an assumed role, that gin matches against a CodeCommit approver; on `codecommit` a member who holds an approving role must set it, and two members cannot share one. Update gin-workflow for every member before adding `permissions`, because an older version rejects the key. `strict: true` makes a missing policy for `requirement_confirmed`, `plan_approved`, or `ship` a configuration error; unset, `setup doctor` and `team init` only warn. `claim_ttl_hours` (integer, minimum 1, default 48) is the lease length `team claim` writes into the bead's `claim` metadata (`holder`, `expires_at`).

### `workspace`

Present when the repository is the parent of several repositories ([guide](../guides/workspace.md)). `repos` lists them: `path` (relative, gitignored in the parent), `url`, `shape` (`frontend`, `backend`, `library`, `qa`, `beads`), `frozen` (read only: no hooks, tracks, or worktrees; cloned shallow), `default_branch` (default `main`), `verify.checks` with the same keys as the root block, and `rules` (`packs`: rule packs added to the root `rules.packs` inside that repository). The `beads` entry sits at `.beads` and holds the shared Beads database. `project.packages` keeps its meaning inside one repository and is ignored for workspace entries. `path` and `url` are required; `shape` is required unless `frozen`. A path is relative, without `..`, not under `.planning` or `.agent-workflow`, and not a duplicate of, or nested inside, another entry. The `beads` shape is accepted only at `.beads`. Check names are the same set as the root `verify.checks`. `gin setup doctor` asks for `verify.checks` on `frontend`, `backend`, and `qa` entries; a `library` entry may have none, and its hooks then run nothing.

### `qa`

Used by the `gin-qa` add-on: `dir` (default `qa`, a path inside the repository), `cases` (default `qa/cases`), `guidelines` (default `qa/guidelines.md`), `e2e` (default `qa/e2e`). `dir` is the QA home of a single repository and is ignored when the workspace has a `shape: qa` child, which is the QA home instead; it needs gin-workflow 3.1 or later. The defaults of the other keys are under the QA home, and an explicit value is relative to the repository that holds it. See [the QA home](../guides/qa.md#the-qa-home).

## `executables.local.yaml`

`setup init` and `setup refresh` record where each external CLI lives on this machine, so a harness whose `PATH` differs from your shell still finds it. Only the tools found are listed.

```yaml
schema_version: "2.11"
executables:
  git: /usr/bin/git
  bd: /home/me/.local/bin/bd
```

A configured path is used while it is an executable file; otherwise the command falls back to `PATH`. A missing or invalid file never fails a command. `setup doctor` reports `stale`, `unconfigured`, `missing`, and `problems` under `checks_details.executables`. The file is not committed and is not exported in bundles. gin-qa does not read it: it imports nothing from gin-workflow and finds `gin` and `npx` on `PATH`.
