💡 Under the Hood: How Detection & Areas Actually Work in Gin-Workflow
Automated Heuristics (project_detect.py): gin-workflow setup detect scans for standard manifests (like package.json, pyproject.toml, pom.xml) and monorepo markers (pnpm-workspace.yaml, package.json workspaces, turbo.json, nx.json).
Handling a Polyglot Monorepo (Java + Node + Playwright): In a modernization monorepo with top-level folders (as-is/, backend/, frontend/, qa/), detect suggests stage: brownfield because manifests and source files already exist. The team then maps each folder to an area with path globs in team.areas; team check-plan rejects a plan track whose files cross areas. Areas are folders of one repository, not separate repositories.

ℹ️ How Usage & Quality Reporting Actually Works

Reports are milestone-based audits, not streaming real-time meters. When a worker finishes a track and closes its bead (bd close at stage execute), gin-workflow usage collect --bead <id> parses local Claude Code/Codex session logs and records the token counts into the bead's metadata. The /report skill is a read-only query across these immutable records, calculating costs and pairing them with review reopens, findings, and waivers.
