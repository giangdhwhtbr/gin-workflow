# Contributing

How to build, install, test, and release the plugins from this repository. By convention, changes to this repository go through its own workflow, `discuss` → `ship`, on a feature branch and never directly on `master`.

## Repository layout

```
.claude-plugin/marketplace.json   Claude Code and Codex marketplace index (git-subdir sources)
plugins/
  gin-workflow/
    plugin.meta.json              name, version, description
    src/
      .claude-plugin/, .codex-plugin/   harness manifests
      agents/                     developer, code-reviewer, docs-writer, ...
      skills/<name>/SKILL.md      stage and support skills (each is a slash command)
      references/                 stage-contract.md, shape-*.md, and docs-style.md, read by skills and agents
      rules/                      rule packs
      templates/                  spec, codebase, and team templates
      examples/                   config.full.yaml
      hooks/hooks.json            pre/post tool hooks
      scripts/                    gin-workflow launcher, workflow_core,
                                  review-ledger.py, review_ledger, hook scripts
    dist/                         generated by the installer (not tracked)
  gin-qa/                         the QA add-on: plugin.meta.json and src/
  gin-orchestrator/               the worker harnesses add-on: plugin.meta.json and src/
    src/
      scripts/                    gin-orchestrator launcher, gin_orchestrator
      skills/providers/           the providers skill
      examples/                   orchestrator.local.example.yaml
docs/                             this documentation
tests/                            unit tests and installer smoke tests
scripts/benchmark/                benchmark helpers
install.sh, install.ps1           build and install
remote-install.sh                 clone-and-install for curl
```

## Build and install locally

`install.sh` rebuilds `plugins/<plugin>/dist/<harness>/` from `src/` and registers it with each harness it finds; it also links the `gin-workflow` (and `gin-qa`, `gin-orchestrator`) launcher into `~/.local/bin`.

Each harness registers differently. Claude Code gets the bundle at `~/.claude/skills/<plugin>`. Codex registers it through its plugin marketplace (`codex plugin marketplace add`, `codex plugin add`), and Antigravity through `agy plugin install`. OpenCode gets the bundle at `~/.config/opencode/skills/<plugin>`, which it scans as a global skills source.

The OpenCode bundle drops the Claude/Codex `agents/` and `commands/` files, so a project install never clobbers a repository's own `.opencode/agents` or `.opencode/commands`. It rewrites the `${PLUGIN_ROOT}` variable to the absolute install path, because shell commands run from the agent's working directory. It renames `report` to `gin-workflow-report` so it does not shadow OpenCode's built-in `report` skill. It ships no `hooks/`, so the safety hook does not run in OpenCode; the CLI still checks the lifecycle gates.

GitHub Copilot CLI registers `dist/copilot/<plugin>` with `copilot plugin install`. That bundle keeps the Claude manifest (`.claude-plugin/plugin.json`) and skills, writes `hooks/hooks.json` in Copilot's format, and drops `agents/` and `commands/`. Its directory carries the plugin name because Copilot names a local install after the source directory.

```bash
./install.sh --platform all                 # build and install for every detected harness
./install.sh --platform codex               # one harness
./install.sh --plugin all                   # gin-workflow, gin-qa, and gin-orchestrator
./install.sh --plugin gin-orchestrator      # installs gin-workflow first when its launcher is missing or at another version
./install.sh --link --platform claude       # symlink the dev tree instead of copying
./install.sh --project /path/to/repo        # install harness files into one repository
./install.sh --dry-run                      # preview
./install.sh --uninstall                    # remove generated dist output, the OpenCode global install, and the Copilot registration
```

`--platform` takes `claude`, `antigravity`, `codex`, `opencode`, `copilot`, `both`, or `all` (default); `--plugin` takes `gin-workflow` (default), `gin-qa`, `gin-orchestrator`, or `all`.

### Windows (PowerShell 7)

Needs PowerShell 7 and Python 3.11 or later as `python` on `PATH`.

```powershell
pwsh -NoProfile -File .\install.ps1 -Platform all
pwsh -NoProfile -File .\install.ps1 -Platform codex -Project C:\path\to\repository
pwsh -NoProfile -File .\install.ps1 -Platform all -DryRun
```

Parameters mirror the shell script: `-Platform`, `-Plugin`, `-Link` (may need Developer Mode or elevation), `-Project`, `-Uninstall`, `-DryRun`. The launcher goes under `$HOME\.local\lib\gin-workflow` with a shim at `$HOME\.local\bin\gin-workflow.cmd`; the installer warns when that folder is not on `PATH` and does not change your environment.

### Refreshing installs after a change

Each harness keeps a snapshot of the plugin taken at install time, so a committed fix reaches a machine only after the installer runs again there: `./install.sh --platform all`. Commit first: the Codex marketplace source reads the committed tree, not your working directory. See [Troubleshooting](reference/troubleshooting.md#a-repository-still-hits-a-gin-workflow-bug-that-was-already-fixed-and-shipped-on-master).

## Tests

```bash
PYTHONPATH=plugins/gin-workflow/src/scripts python3 -m unittest tests/test_all.py
bash tests/install_smoke_test.sh
```

`tests/test_all.py` runs every suite under `tests/workflow_core`, `tests/gin_orchestrator` (the gin-orchestrator plugin), `tests/review_ledger`, and `tests/gin_qa` (Playwright tests skip without a Playwright environment), plus the other `tests/test_*.py` files. The smoke test builds and installs into temporary homes. `tests/install_smoke_test.ps1` is the Windows counterpart.

To run one file, pass its path, for example `PYTHONPATH=plugins/gin-workflow/src/scripts python3 -m unittest tests/workflow_core/test_atomic.py`. `-k` does not narrow `tests/test_all.py`, because its `load_tests` builds its own loader.

`tests/workflow_core/test_docs_coverage.py` checks these docs against the code:

- every skill appears in [reference/skills.md](reference/skills.md), and every `gin-workflow` subcommand has a heading in [reference/cli.md](reference/cli.md);
- every page under `docs/` is linked from `README.md`;
- relative links resolve, including in the plugin READMEs;
- Mermaid blocks name a diagram type;
- no line calls Beads the default or required, unless it also says optional;
- no page mentions the removed worker-routing key of the old schema or the removed Telegram shell script.

Adding a skill or a subcommand means documenting it.

`tests/workflow_core/test_token_budget.py` caps sizes: each shared `gin-*` skill at 6,000 characters, each agent at 4,000, and each stage skill with the references it links at 13,500 (`quick` at 8,000). The gin-qa and gin-orchestrator skills stay within 6,000 characters each, and the core never names `gin-qa` (`tests/gin_qa/test_packaging.py`, `tests/gin_orchestrator/test_orchestrator_packaging.py`). Skills and agents reach tasks through `gin-workflow task`, never `bd` directly, except the Beads-only skills (`tests/test_no_direct_bd.py`).

## Releasing

1. Bump the plugin version in `plugins/<plugin>/plugin.meta.json`, `src/.claude-plugin/plugin.json`, and `src/.codex-plugin/plugin.json`; for `gin-orchestrator` also `ORCHESTRATOR_VERSION` in `src/scripts/gin_orchestrator/cli.py`. When a CLI changed, also bump its launcher version: `LAUNCHER_VERSION`, `QA_LAUNCHER_VERSION`, or `ORCH_LAUNCHER_VERSION` in `install.sh`, the matching `$LauncherVersion`, `$QaLauncherVersion`, or `$OrchLauncherVersion` in `install.ps1`, and the version the CLI prints (`CLI_VERSION` in `workflow_core/cli.py`, `VERSION` in `gin_qa/cli.py`). Then update the version assertions in `tests/install_smoke_test.sh`, `tests/install_smoke_test.ps1`, `tests/gin_orchestrator/test_harness_packaging.py`, and, for `gin-orchestrator`, `test_orchestrator_packaging.py`, `test_contract_cli.py`, and `test_contract_v2.py`.
2. Run the tests and the smoke test.
3. Merge to `master` with approval and push.
4. Tag the merge commit `vX.Y.Z` (the `gin-workflow` version) and push the tag: `git tag vX.Y.Z && git push origin vX.Y.Z`. `.github/workflows/release.yml` fails unless the tag equals the version in `plugins/gin-workflow/plugin.meta.json`, runs the full test suite, then creates the GitHub release with generated notes. `gin-qa` and `gin-orchestrator` ship in the same release under their own versions.
5. Reinstall on each machine (`./install.sh --platform all`); marketplace users update through their harness.

## Benchmarks

Benchmarks compare the token cost and outcome of gin-workflow with other agent workflows on the same tasks. The procedure below is a convention: runs are manual, and CI does not run them.

- Use one pinned React + TypeScript + Vite repository as the sample; record its URL and commit SHA, and start every run from a clean checkout.
- Run two tasks: a small bug fix (a failing test or reproducible symptom) and a medium feature (one component, its state handling, and tests). Write each prompt once and reuse it verbatim.
- Compare four configurations: `gin-easy` (rigor `easy`, `/quick`), `gin-standard` (rigor `standard`, full lifecycle), `superpowers` (its default flow), and `spec-kit` (its default flow). Use the same harness and model for all, and record the framework versions.
- Measure input, output, cache-write, and cache-read tokens; tool calls; wall time; and whether the task's tests pass. Report a run whose tests fail as failed.
- Collect the numbers with `python3 scripts/benchmark/summarize_usage.py gin-easy=<session.jsonl> superpowers=<session.jsonl>`. It prints a Markdown table with one row per label, read from Claude Code transcripts (`~/.claude/projects/<project>/<session>.jsonl`).
- Write each benchmark to `docs/benchmarks/YYYY-MM-DD-<sample>.md` with the sample commit, prompts, framework versions, the table, and each run's test outcome.
