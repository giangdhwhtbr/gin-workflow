# Contributing

How to build, install, test, and release the plugins from this repository. This repository uses its own workflow: changes go through `discuss` → `ship` on a feature branch, never directly on `master`.

## Repository layout

```
.claude-plugin/marketplace.json   Claude Code and Codex marketplace index (git-subdir sources)
plugins/
  gin-workflow/
    plugin.meta.json              name, version, description
    src/
      .claude-plugin/, .codex-plugin/   harness manifests
      agents/                     developer, code-reviewer, docs-writer, ...
      skills/<name>/SKILL.md      stage and support skills (each is a slash command)
      references/                 stage-contract.md and shape-*.md, read by skills
      rules/                      rule packs
      templates/                  spec, codebase, and team templates
      examples/                   config.full.yaml, providers.local.example.yaml
      hooks/hooks.json            pre/post tool hooks
      scripts/                    gin-workflow launcher, workflow_core, workflow_providers,
                                  review-ledger.py, review_ledger, hook scripts
    dist/                         generated by the installer (not tracked)
  gin-qa/                         the QA add-on, same structure
docs/                             this documentation
tests/                            unit tests and installer smoke tests
scripts/benchmark/                benchmark helpers
install.sh, install.ps1           build and install
remote-install.sh                 clone-and-install for curl
```

## Build and install locally

`install.sh` rebuilds `plugins/<plugin>/dist/<harness>/` from `src/` and registers it with each harness it finds; it also links the `gin-workflow` (and `gin-qa`) launcher into `~/.local/bin`.

Each harness registers differently: Claude Code gets the bundle at `~/.claude/skills/<plugin>`, Codex and Antigravity register through their plugin marketplaces, and OpenCode gets the bundle at `~/.config/opencode/skills/<plugin>`, which it scans as a global skills source. The OpenCode bundle drops the Claude/Codex `agents/` and `commands/` files (so a project install never clobbers a repository's own `.opencode/agents` or `.opencode/commands`), rewrites the `${PLUGIN_ROOT}` variable to the absolute install path (shell commands run from the agent's working directory), and renames `report` to `gin-workflow-report` so it does not shadow OpenCode's built-in `report` skill.

```bash
./install.sh --platform all                 # build and install for every detected harness
./install.sh --platform codex               # one harness
./install.sh --plugin all                   # gin-workflow and gin-qa
./install.sh --link --platform claude       # symlink the dev tree instead of copying
./install.sh --project /path/to/repo        # install harness files into one repository
./install.sh --dry-run                      # preview
./install.sh --uninstall                    # remove generated dist output and the OpenCode global install
```

`--platform` takes `claude`, `antigravity`, `codex`, `opencode`, `both`, or `all` (default); `--plugin` takes `gin-workflow` (default), `gin-qa`, or `all`.

### Windows (PowerShell 7)

Needs PowerShell 7 and Python 3 as `python` on `PATH`.

```powershell
pwsh -NoProfile -File .\install.ps1 -Platform all
pwsh -NoProfile -File .\install.ps1 -Platform codex -Project C:\path\to\repository
pwsh -NoProfile -File .\install.ps1 -Platform all -DryRun
```

Parameters mirror the shell script: `-Platform`, `-Plugin`, `-Link` (may need Developer Mode or elevation), `-Project`, `-Uninstall`, `-DryRun`. The launcher goes under `$HOME\.local\lib\gin-workflow` with a shim at `$HOME\.local\bin\gin-workflow.cmd`; the installer warns when that folder is not on `PATH` and does not change your environment.

### Refreshing installs after a change

Each harness keeps a snapshot of the plugin taken at install time, so a committed fix reaches a machine only after the installer runs again there: `./install.sh --platform all`. Commit first: the Codex marketplace source reads the committed tree, not your working directory. See [Troubleshooting](reference/troubleshooting.md#a-repository-still-hits-a-gin-workflow-bug-that-was-already-fixed-and-shipped-on-master).

## Tests

```bash
PYTHONPATH=plugins/gin-workflow/src/scripts python3 -m unittest tests/test_all.py
bash tests/install_smoke_test.sh
```

`tests/test_all.py` runs every suite under `tests/workflow_core`, `tests/workflow_providers`, `tests/review_ledger`, and `tests/gin_qa` (Playwright tests skip without a Playwright environment). The smoke test builds and installs into temporary homes. `tests/install_smoke_test.ps1` is the Windows counterpart.

`tests/workflow_core/test_docs_coverage.py` keeps these docs honest: every skill must appear in [reference/skills.md](reference/skills.md), every `gin-workflow` subcommand needs a heading in [reference/cli.md](reference/cli.md), relative links must resolve, and Mermaid blocks must name a diagram type. Adding a skill or a subcommand means documenting it.

Skills stay under 6,000 characters each; the core never names `gin-qa`.

## Releasing

1. Bump the version in `plugins/<plugin>/plugin.meta.json`, `src/.claude-plugin/plugin.json`, and `src/.codex-plugin/plugin.json` (for `gin-qa` also `src/scripts/gin_qa/cli.py`), plus the launcher version in `install.sh` (`LAUNCHER_VERSION`, `QA_LAUNCHER_VERSION`) and `install.ps1` (`$LauncherVersion`, `$QaLauncherVersion`) when the CLI changed, and the version assertions in `tests/install_smoke_test.sh`, `tests/install_smoke_test.ps1`, and `tests/workflow_providers/test_harness_packaging.py`.
2. Run the tests and the smoke test.
3. Merge to `master` with approval and push.
4. Tag the merge commit `vX.Y.Z` (the `gin-workflow` version) and push the tag: `git tag vX.Y.Z && git push origin vX.Y.Z`. `.github/workflows/release.yml` fails unless the tag equals the version in `plugins/gin-workflow/plugin.meta.json`, runs the full test suite, then creates the GitHub release with generated notes. `gin-qa` ships in the same release under its own version.
5. Reinstall on each machine (`./install.sh --platform all`); marketplace users update through their harness.

## Benchmarks

Compares the token cost and outcome of gin-workflow with other agent workflows on the same tasks. Runs are manual, not part of CI.

- **Sample**: one pinned React + TypeScript + Vite repository; record its URL and commit SHA, and start every run from a clean checkout.
- **Tasks**: a small bug fix (a failing test or reproducible symptom) and a medium feature (one component, its state handling, and tests). Write each prompt once and reuse it verbatim.
- **Configurations**: `gin-easy` (rigor `easy`, `/quick`), `gin-standard` (rigor `standard`, full lifecycle), `superpowers` (its default flow), `spec-kit` (its default flow); same harness and model for all, framework versions recorded.
- **Metrics**: input, output, cache-write, and cache-read tokens; tool calls; wall time; whether the task's tests pass. A run whose tests fail is reported as failed, not as cheaper.
- **Collecting**: `python3 scripts/benchmark/summarize_usage.py gin-easy=<session.jsonl> superpowers=<session.jsonl>` prints one Markdown table row per label from Claude Code transcripts (`~/.claude/projects/<project>/<session>.jsonl`).
- **Recording**: write each benchmark to `docs/benchmarks/YYYY-MM-DD-<sample>.md` with the sample commit, prompts, framework versions, the table, and each run's test outcome.
