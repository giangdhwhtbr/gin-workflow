# Story points: AI-scored size, days from the measured pace, velocity KPIs

**Context**
Epic `gin-workflow-y7d6` (2026-11-19). Roadmap epics were estimated in working days (`estimated_minutes`), which mixes size with pace; with AI agents the pace moves, so day estimates went stale. The team works in Scrum terms and needs velocity KPIs, shown on gin-console by `gin-console-ulf` under the cross-repo epic `gin-harness-vhl` (export `story-points`).

**Decision/Solution**
- Points live in epic bead metadata: `points` (scale `POINT_SCALE` 1, 2, 3, 5, 8, 13, 21), `points_reason`, `points_history` (`{from, to, stage, at, actor}`, appended like `milestone_moves`; bd returns it as a string or a list). Written only by `gin points EPIC N --reason TEXT [--stage roadmap|discuss|close]` (`points_cli.py`, since `gin-workflow-05e5`), which accepts any open epic and refuses off-scale or non-ASCII digits, an empty reason, a missing bead, a non-epic, a closed epic, and an epic whose milestone has `kickoff` unless `--stage close`, all before any bd write. `gin milestone points` forwards to it before argparse, so it is missing from `gin milestone --help` and its errors start with `points error:`. It reuses `milestone_cli._write` (role guard on `team.permissions.milestone`, pull, push) through its `write=` argument, and calls `milestone_cli._bd` at call time so `mock.patch.object(milestone_cli, "_bd")` still applies.
- Days are derived, never stored: `epic_days(epic, pace)` is `ceil(round(points * pace.value, 6))`, at least 1, else the old `estimated_minutes`. A `Pace` (`value`, `measured_epics`, `assumed`) is threaded as keyword `pace=DEFAULT_PACE` through `remaining_days`, `_planned_days`, `schedule`, `show_payload`, `forecast`, `list_payload`, so callers and epics without points behave as before.
- `measure_pace(beads, assumed, today)`: the 10 (`MEASURED_EPICS`) most recently closed epics with points and actual days, whatever their labels (`roadmap` only until `gin-workflow-05e5`), sum of working days `started_at`..`closed_at` (both included, at least 1) over sum of points; else the roadmap line `- Days per point: <n>` (read by `roadmap_file.py` into `Roadmap.days_per_point`), else 1, assumed.
- `gin milestone estimate` refuses an epic with points. `kickstart` writes `committed_points` (open epics' points) and `planned_days_per_point`, and warns only when a re-kick-start changes the commitment.
- `velocity(milestone, beads, today)`: `committed_points`, `completed_points` (closed epics with points), `added_points` (latest `milestone_moves` entry into the milestone dated after `kickoff`), `say_do`, `days_per_point` (closed epics with points and actual days), `planned_days_per_point`, `accuracy` = planned over measured. Nulls instead of division by zero; malformed snapshot keys are reported by `metadata_problems`.
- JSON is additive, `schema` stays 1: top-level `days_per_point`, per-milestone `velocity`, epic rows `points`, `points_reason`, `estimate_source` (`points`|`days`|`assumed`, null for a closed epic with neither), `actual_days`, `actual_days_per_point`.
- Skills: `roadmap/references/story-points.md` holds the scoring guide (drivers, anchors from every closed epic with points, split above 21, `PM:` reason on a correction, write, score in `/discuss`, lock). `/roadmap` writes `Points:` and `Estimate:` per epic and calls `gin points`; `/milestone-close` reports `velocity`, `say_do`, `days_per_point`, `accuracy` and corrects points with `--stage close`.
- Every workflow is scored once, in `/discuss`, into a `Points: <n> (<reason>)` header line under `Kind:` of the design spec, technical design, or SDD `01-proposal.md` (the three templates carry it), so the score is reviewed with the spec, in chat or in the spec PR. It is written with `gin points ... --stage discuss` once `requirement-confirmed` is recorded and an epic exists: `/discuss` step 8 for `/discuss <epic-id>` and the SDD epic, `/orchestrate` for the epic it creates (copied, never re-scored). Lock, role, and markdown-backend refusals are reported and never block the stage. `skills/sdd/SKILL.md` is unchanged (5,990 of 6,000 characters); the rule reaches the SDD layout through the **Points** paragraph of `discuss/SKILL.md`, which sits outside steps 5-8.

**Consequences**
- Size caps after `gin-workflow-05e5`: roadmap `SKILL.md` 11,788 of 12,000, `milestone-plan.md` 3,530 of 4,000, `story-points.md` 3,370 of 4,000, discuss chain 11,549 of 12,000, orchestrate chain 8,848 of 12,000.
- A legacy spec that keeps the template's `Points: {{points}} ...` placeholder fails `gin specs lint` (`lint_design_spec` flags `{{`), which forces the score before `requirement-confirmed`; SDD `specs new` leaves the placeholder in `01-proposal.md` and no lint checks it there. `discuss` names `../roadmap/references/story-points.md` as inline code, not a markdown link, so `budget.stage_chain` does not load it.
- An additive JSON key breaks the exact-payload tests in `test_milestone.py` (`PayloadTests`) and `test_milestone_cli.py` (`test_req_011_*_exact_payload`); the track that adds keys must own both files (see [milestone-lanes-and-forecast](milestone-lanes-and-forecast.md)).
- `str.isdigit()` accepts characters such as `²` that `int()` rejects; metadata and CLI input parse digits with `isascii() and isdigit()`.
- gin-console's Reports page reads `estimated_minutes` from bd; epics with points have none until `gin-console-ulf` switches to `estimate_days` from `gin milestone --json`. The gin-console contract doc in gin-harness is updated there.
