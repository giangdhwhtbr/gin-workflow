# Milestone lanes and the roadmap forecast: a project deadline next to sprint milestones

**Context**
Epic `gin-workflow-57fw` (2026-11-08). Milestones are sprints, so a project-wide deadline had no home. The scheduler in `workflow_core/milestone.py` let independent epics start on the same day without limit (optimistic, not sequential as the epic description assumed), `AI capacity:` in the roadmap was free text the CLI never read, and unassigned roadmap epics were only counted. The user's flow: `/roadmap` for the whole project first, then `gin milestone create` plus `/roadmap --milestone <id>` to pick ready epics into each sprint.

**Decision/Solution**
- A lane is one stream of work that runs one epic at a time. `_place(epics, first, lanes)` is the one greedy placer: the ready epic with the earliest allowed start (ties by id) takes the lane that frees first; since `gin-workflow-milestone-gates` it takes a `days` mapping from `_planned_days` (remaining days for in-progress epics, an assumed median for open unestimated ones; only closed unestimated epics take no lane); the lane list is capped at the number of epics (a huge `lanes` metadata value set through `bd` caused OOM in review). `schedule` and `show_payload` take `default_lanes` and use `lanes_of(milestone, default_lanes)`.
- Lanes per milestone live in the milestone's `lanes` metadata (`gin milestone create/update --lanes N`, positive whole number, empty value refused). Effective lanes: metadata, else the whole number that starts the roadmap `AI capacity:` line, else the number of `team.members` holding a building role (`dev`, `be_*`, `fe_*`, `*_dev`, `*_lead`; `milestone.is_building_role`, since `gin-workflow-milestone-capacity`), else 1 (`milestone_cli._default_lanes`).
- `workflow_core/roadmap_file.py` reads only two bullets of the roadmap file (`team.ROADMAP[layout]`): `- Deadline: YYYY-MM-DD` and the leading number of `- AI capacity:`. It never raises: a missing file or line gives None, a malformed date or unreadable file fills `Roadmap.error`. `Roadmap` is a frozen dataclass in `milestone.py` to avoid a circular import.
- `forecast(beads, today, roadmap, default_lanes)` schedules open milestones in `end` order, each on its own lanes, one after another from `max(today, kickoff or start, previous finish + 1 working day)`, then every open roadmap epic outside an open milestone on the default lanes. Milestones with no open epics are skipped before their dates are parsed. On a cycle or bad milestone metadata, `error` is set and `finish` covers only the groups placed before it. `list_payload` adds per-entry `lanes` and top-level `forecast` (null without an open roadmap epic); `schema` stays 1.
- `gin milestone list` ends with `forecast: finish <date>, deadline <date>, N working days spare | overflow N working days | on the deadline, lanes N, N open epics[, N unestimated]`; `no deadline` without the line; `finish unknown` only when no epic can be placed (unestimated open epics now take assumed days); `forecast: error: ...` replaces the dates. `list` exits 0 in every case.
- `/roadmap` asks for the deadline next to AI capacity, proposes `Estimate:` for every epic in the plain run too (written with `gin milestone estimate` when Beads has none; Beads wins otherwise), asks a sprint's lanes in `--milestone`, and reports `forecast` from `gin milestone list --json` without computing dates itself.

- `gin-workflow-milestone-gates` (2026-11-10): `_confirmed(root, beads)` treats a spec as confirmed from the bead's `gates.requirement_confirmed` (via `team_beads.gates_of`, no extra `bd` call) or the local event; `spec_due` warns open unconfirmed epics of a `planned` milestone starting within `SPEC_DUE_DAYS = 5` working days; `remaining_days` is `ceil(estimate * open tracks / all tracks)` or the estimate minus working days since `started_at`, at least 1; the assumed median is taken over estimated, not-closed epics of the same group (milestone or pool) so `show` and the forecast agree; `show` adds `deadline`; rows add `remaining_days` and `assumed_days`. `record orchestration-ready --epic` writes `gates.orchestration_ready` and `gin state` merges it in team mode. Spec `.planning/specs/2026-11-10-milestone-gates-design.md`.
- `gin-workflow-milestone-capacity` (2026-11-10): days off live in the milestone's `away` metadata (`gin milestone update --away MEMBER:FROM[..TO]|MEMBER:none`, member = email key of `team.members`; `none` also removes a member who left the team). They apply only when the lanes come from building members (no valid `lanes` metadata, no `AI capacity:` number): lane n is the n-th builder, `_place(..., off)` picks the lane by its effective start and skips the epic-count lane cap, and `forecast` applies the same `off` to milestone groups (not the pool). `--integration YYYY-MM-DD|none` stores `integration`; `schedule` warns `after_integration` (open epic ending after it), `open_bugs` with `count` (open `bug` beads whose own `dependencies` hold `type: discovered-from`, `depends_on_id: <epic>`), and `oversized` with `days` (planned days over the milestone's working days). Malformed `away`/`integration` are ignored with `warning: <id>: malformed <key> metadata ignored` (`metadata_problems`). The roadmap skill names `oversized` epics at adoption and the Load block counts QA. Spec `.planning/specs/2026-11-10-milestone-capacity-design.md`.

**Consequences**
- Roadmap `SKILL.md` is at 11,985 of 12,000 characters after `gin-workflow-milestone-capacity`; a trim there once dropped a rule ("neither counts" without its two subjects) and review caught it. Any further skill text needs an equal cut elsewhere, checked against rule loss.
- Open (not tracked as a bead): `_off` walks every away day, and the lane key evaluates it for each lane, so a typo range of centuries costs seconds per command; capping the range length in `_away_change` would fix it.
- Review lesson (`gin-workflow-milestone-gates`): adding a test class between a decorator and the class it decorates silently moves the decorator; adding a class with an existing name shadows the old one; a class after `if __name__ == "__main__"` is skipped when the file runs directly. Reviewers caught all three; check `--collect-only` counts when tests are added.
- Open suggestions from the review of track .2: the `workflow:<id>` label is applied after the gate writes, so a failing gate write skips it (same as the earlier proofs loop); no test covers a failing `orchestration_ready` write.
- Milestones planned before lanes existed show later dates and may gain `overflow` warnings at the default of 1 lane; `--lanes` or the `AI capacity:` number is the remedy (cli.md says so).
- The forecast pool is broader than `unassigned_epics`: it also holds open roadmap epics under a closed milestone or a non-milestone parent.
- Group sequencing makes a cross-group blocker rule unnecessary: an earlier group always finishes before the next starts; a sprint epic blocked by a pool epic is not moved (`show` warns `external_blocker`).
- `gin evidence run` runs the whole suite (about 4.5 minutes), so a track that changes a payload must update the exact-payload CLI tests in the same track, or evidence fails; tracks 2 and 3 did that although the plan put it in track 4.
- Roadmap `SKILL.md` grew to 10,714 characters; it is outside `budget.STAGES`, so no test enforces its size.
- The installed `gin` at `~/.local/bin` lags the repo until `install.sh` runs; run `plugins/gin-workflow/src/scripts/gin` for a manual check in a worktree.
- Follow-ups: gin-console reads the new keys through a `gin-harness` epic depending on `external:gin-workflow:milestone-forecast` (the Pydantic models ignore unknown keys until then); the brownfield guide describes the two-step roadmap flow in `gin-workflow-docs-refresh`.
