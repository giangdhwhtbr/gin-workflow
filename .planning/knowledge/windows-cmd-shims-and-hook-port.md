# Windows: spawning .cmd shims, UTF-8, and porting the safety hook

**Context**
Epic `gin-workflow-rm-windows-parity` (2026-11-02) made the CLI, the safety hook, and gin-orchestrator workers run on Windows without Git Bash. Three design points came out of review and cost a review cycle each; they apply to any future code that starts a process on Windows or parses shell text in Python.

**Decision/Solution**
- An npm CLI on Windows is a `.cmd` shim, and `cmd.exe` re-parses the whole command line. `NativeCliRunner` therefore runs a `.cmd`/`.bat` as one string: `"<SystemRoot>\System32\cmd.exe" /d /s /v:off /c "<args>"`, every argument wrapped in double quotes with a trailing backslash run doubled, and it refuses up front any argument that contains `"`, `%`, `\r`, `\n` or makes the line longer than 8191 characters (`NativeCliError(SERVICE, "argument cannot be passed safely through cmd.exe")`). `subprocess.list2cmdline` is not enough: it leaves `& | < > ^` unquoted when the argument has no space. Workers that pass the prompt in argv (opencode, antigravity) hit the refusal when their CLI is only a shim; the prompt belongs on stdin.
- The CLI process runs in UTF-8 mode from the shim (`py -3 -X utf8` or `python -X utf8`) and the Windows CI job sets `PYTHONUTF8=1`, so no `subprocess(text=True)` call needs `encoding=`.
- `executable_resolver` probes `PATHEXT` extensions before the bare name on `nt`; `PATHEXT` is always `;`-separated regardless of `os.pathsep`, and `os.access(X_OK)` is only an existence check on Windows, so the bare `claude` sh script would otherwise win over `claude.cmd`.
- `hooks._run_commands` splits a leading `NAME=value` prefix into the child environment only when the value has no quote, `$`, backtick, `;`, `|`, `&`, `<`, `>`, `(`, `)` or backslash; anything else goes to the shell unchanged.
- Windows CI (`.github/workflows/test.yml`, track `.5`) found five product bugs that no Linux test could: `msvcrt.locking` is mandatory, so a lock must never read or write the byte it locks (EACCES under contention); `Path.home()` raises `RuntimeError` when neither `USERPROFILE` nor `HOME` is set, which crashed `executable_resolver` at import; `subprocess` does not find `npm` without `shutil.which` because it is `npm.cmd`; `:` is not valid in a Windows file name, so `task_markdown` rejects it in ids on `nt`; paths shown to the user go through `as_posix()`. CI details: `unittest discover -s tests` imports `tests/gin_orchestrator` as a top-level package and shadows the plugin package, so CI runs `tests/test_all.py` with `PYTHONPATH`; the runner's `TEMP` is an 8.3 short path (`RUNNER~1`), so the job sets `TEMP`/`TMP` to `runner.temp` at step level (`runner` is not available in job-level `env`); the installed shim prefers `py -3`, so PyYAML is installed with `py -3 -m pip`. Fake CLIs written as `#!` scripts skipped about 146 tests on Windows until `gin-workflow-myd7` (epic `gin-workflow-rrui`, 2026-11-03) gave them `.cmd` wrappers; the Windows job then went from `skipped=250` to `skipped=104`.
- Running the fakes as `.cmd` wrappers reproduced the shim problem outside `NativeCliRunner`: `CliTaskTrackingProvider.close_task` passes quoted JSON in `--append-notes=...` through `subprocess.run([shim, ...])`, cmd.exe re-parses it, and `gin-workflow task update` prints nothing with exit 0 (`gin-workflow-gscr`). Any code that spawns a `.cmd` shim with `"` in an argument needs the `NativeCliRunner` treatment or stdin. A test that spawns a fake on Windows must pass the path `shutil.which` returns (the `.cmd`), never the bare name: `CreateProcess` appends only `.exe`. A child whose `PATH` is built from `os.defpath` has no `git` on Windows (`os.defpath` is `.;C:\bin`); `tests/gin_qa/qa_fixtures.TOOLS_PATH` adds git's directory.
- `safety_check.py` parses the command one character per byte (UTF-8 bytes mapped through latin-1) to match `LC_ALL=C` in the old bash script, and its `--no-veri`, `commit -n`, and `sh -c` checks scan in linear time (`in_order`, `wrapped_payloads`). A direct translation of the bash regexes backtracked quadratically in Python's `re`: a 30K-character command exceeded the 30 s hook timeout, which fails open.

**Consequences**
- Tests that patch `os.name = "nt"` on Linux must build every `Path` before the patch and use `os.path` inside the code under test; `pathlib` raises `NotImplementedError` for `WindowsPath` on POSIX.
- A parity port of a security check needs a differential oracle (the old script kept in a scratch dir and run on fuzzed inputs), plus a long-input timing test; equivalence on the unit tests alone missed the timeout.
- Real Windows behavior of the shim line and `taskkill /T` is only proven by the `windows-latest` job; every local test mocks `Popen`.
- The test workflow runs only on `workflow_dispatch` since 2026-11-08 (Actions minutes); the release workflow still runs the unit tests on every tag. Bug `gin-workflow-bvhv` (2026-11-08) fixed the Windows job after it was red for a day: compare a git-printed path with a `Path`, never a string; a `#!` stub on `PATH` skips on `nt` with a named reason; build a fixture URL from the same `Path` the fixture was written with; write a fixture whose newline style the code preserves with `newline="\n"`; never assert `setup doctor` overall `status`, which depends on the harness CLI being on the runner's `PATH` (only the Linux job stubs `claude`). The Linux smoke test failed because `QA_LAUNCHER_VERSION` was not bumped with `gin_qa/cli.py`; `tests/test_version_pins.py` now ties the installer pins, the CLI constants, and the smoke tests together. The last Windows failure (`gin-workflow-decc`) was not Windows-specific: since the add-on refresh (`gin-workflow-fdnl`), a `--project` install also ran `Install-Plugin` for the managed gin-qa, whose `setup` skill replaced gin's in the project's shared `.opencode/skills`; only the ps1 smoke test orders a project install after the global gin-qa install. Both installers now refresh the add-on launchers on every install and skip the add-on plugin files when a project is set. The smoke tests are the only cross-platform check of the installers, so a new case belongs in both `tests/install_smoke_test.sh` and `.ps1`, in the same order.
