# Use cases and activity diagrams that match a BA's SRS

Workflow: srs-ba-alignment
Kind: capability
Status: confirmed by the user on 2026-11-15 (revised after a BA review).

## Goal and scope

With the SDD layout, a capability holds use cases (`<specs>/<cap>/use-cases/<slug>.md`, spec `2026-11-09-use-cases-design.md`) and activity diagrams (`<specs>/<cap>/diagrams/<feature>-activity.md`, spec `2026-11-05-spec-diagrams-design.md`), and `gin specs export` prints both in the SRS. Compared with the SRS a business analyst writes, four things are missing:

- the use case template has no trigger, secondary actors, exception flows, business rules, or include/extend relations;
- the SRS has no use case diagram (actors, use cases, system boundary, include/extend);
- the activity template shows no swimlanes, does not require a guard on each branch of a decision, and does not say which use case it draws;
- lint asks for one activity diagram per capability, while the `sdd` skill asks for one per feature: a second feature of a capability passes without its own diagram.

Confirmed decisions (2026-11-15):

- A use case's slug (its file name without `.md`) is its ID. No `UC-` numbering; the 2026-11-09 decision stands.
- The use case diagram is generated by `specs export` from the use case files and never stored.
- The new use case lines and sections are optional. Lint checks only that `Includes:`, `Extends:`, and `Use case:` name an existing use case.
- Feature-level lint has two rules: a change updates an activity diagram of each capability it changes, and each use case it adds or modifies is drawn by an activity diagram that names it.
- Lint checks that each edge leaving a decision node has a label.
- A `technical` change skips every change-level diagram and use case rule, including the existing one.

Revised after a BA review (2026-11-15), confirmed by the user:

- A use case that another use case of its capability includes needs no `Actor:`; the diagram draws an actor edge only where `Actor:` is present, so an included use case is not shown as started by an actor.
- The capability rule of R4 applies to `ADDED` blocks only: a `MODIFIED` block that changes a value does not force a diagram edit.
- A changed use case needs its own activity diagram only when it has an alternative or exception flow.
- The activity template declares each node inside its lane and writes the edges between lanes after the last `end`; decision labels start with the flow ID.
- Actor names are matched without regard to case or repeated spaces; the diagram labels edges `«include»`/`«extend»` and styles actors apart from use cases.

Out of scope (BA review findings for the follow-up epic gin-workflow-414v: an include across capabilities, actor and use case generalization, glossary, NFRs, actor catalogue, business rules catalogue, a UC↔REQ↔test traceability matrix, revision history, a context diagram, diagrams pre-rendered for offline PDF):
- `/gin:explain` (`specs_explain.py`) and the `gin-ba` plugin.
- A command that prints or writes the use case diagram to a file.
- Validating Mermaid syntax beyond the decision-edge labels of R4.
- Swimlane enforcement: lanes are a template convention.
- The legacy layout, which has no living specs and no SRS.

## Requirements

### R1. Use case template

`gin specs template use-case.md` prints:

```markdown
# <Use case name>

Actor: <primary actor>
Secondary actors: <actor>, …
Trigger: <event that starts the use case>
Requirements: REQ-<CAP>-NNN, …
Includes: <slug>, …
Extends: <slug>, …

## Goal
## Preconditions
## Main flow
1. …
## Alternative flows
### 2a. <condition>
## Exception flows
### 3e. <error or failure>
## Business rules
## Postconditions
```

The template comment says:
- which lines are optional: `Secondary actors`, `Trigger`, `Includes`, `Extends`, the sections other than `## Main flow`, and `Actor` for a use case that another use case includes;
- that a slug is the file name of another use case of the same capability, and that an unused optional line is deleted, not left empty;
- that the main flow step where an included use case runs says `Include <slug>`;
- that `Extends:` names the use case this one extends, and `Trigger:` gives the extension point and condition (`At step 3 of <slug>, when …`);
- that a time-triggered use case has the actor `Scheduler`, never `System`;
- that `## Business rules` cites REQ-IDs instead of restating rules;
- that each alternative or exception flow ends with `Resume at step N` or `Use case ends`.

The example flows end with those lines.

`Secondary actors:`, `Includes:`, and `Extends:` hold comma-separated values; surrounding spaces are ignored.

### R2. Activity template

`gin specs template activity.md` prints a template whose comment and example show:

- an optional `Use case: <slug>` line under the title, naming the use case of the same capability that the diagram draws;
- one `subgraph` per lane (an actor or the system), each node declared inside its lane, and the edges between lanes written after the last `end`;
- a start node `((Start))` and an end node `(((End)))`;
- a label on each edge leaving a decision node, in the form `-->|<condition>|`, starting with the flow ID of the use case when there is one (`-->|2a invalid|`).

The Mermaid block still starts with `flowchart`.

### R3. Reference lint

`specs lint` (living and `--change`) no longer reports a missing `Actor:` line in a use case whose slug is on the `Includes:` line of another use case of the same capability; every other use case still needs one.

`specs lint` (living and `--change`) reports, for every file under `<specs>/<cap>/`:

- an `Includes:` or `Extends:` value in `use-cases/<slug>.md` that is not the slug of a file in the same capability's `use-cases/`, or that is the file's own slug;
- a `Use case:` value in `diagrams/*-activity.md` that is not the slug of a file in the same capability's `use-cases/`.

Format: `docs/specs/orders/use-cases/pay.md: Includes names unknown use case 'verify-otp'`.

An empty optional line (`Includes:` with no value) is not a finding.

### R4. Change lint

`specs lint --change <epic> [--against <base>]` and `specs archive` apply these rules when the change's kind (`change_kind`, from `01-proposal.md`) is not `technical`. A `technical` change gets none of them, including the existing one in the first bullet.

Without `--against`:
- unchanged: each capability with an `ADDED` or `MODIFIED` block in the delta has a `diagrams/*-activity.md`.

With `--against <base>`, a file is *changed* when it does not exist at `<base>` or its working-tree content differs from its content at `<base>`. Instead of the rule above:
- each capability with an `ADDED` block in the delta has a changed `diagrams/*-activity.md`: `orders: no activity diagram added or changed in docs/specs/orders/diagrams/ since master (gin specs template activity.md)`;
- each changed `use-cases/<slug>.md` that has a `### ` heading under `## Alternative flows` or `## Exception flows` is named by the `Use case:` line of an activity diagram in its capability: `docs/specs/orders/use-cases/pay.md: no activity diagram with 'Use case: pay'`;
- in each changed `diagrams/*-activity.md`, each edge whose source is a decision node (a node defined anywhere in the block with `{…}`) has a label (`-->|x|`, `-- x -->`, `-.->|x|`, `-. x .->`, `==>|x|`, `== x ==>`): `docs/specs/orders/diagrams/pay-activity.md:12: edge from decision 'stock' has no label`. An edge is read per line; on a chained line (`a --> b --> c`) only its first edge is checked. Lines inside `%%` comments are skipped.

A `parity` change follows the same rules; they apply only to the capabilities and use cases its delta and files touch.

### R5. Use case diagram in the SRS

`specs export` builds, for each capability with at least one `use-cases/*.md`, a Mermaid block placed at the start of the `{{use_cases}}` value in `<section class="use-case-diagram" id="<cap>-use-case-diagram">`:

- `flowchart LR`;
- a `subgraph` titled with the capability title (the `# ` line of `spec.md`), holding one node per use case, shaped `(["<use case title>"])`, sorted by slug;
- one node per distinct actor, outside the subgraph; names that differ only in case or repeated spaces are one actor, labelled with the first spelling met in slug order; actor nodes get `classDef actor` (a plain box with a thick border) so they read apart from use cases;
- an edge from the primary actor (`Actor:`) to the use case, only when the use case has an `Actor:` line; an edge from the use case to each secondary actor;
- `-. «include» .->` from a use case to each slug on its `Includes:` line, and `-. «extend» .->` from a use case to each slug on its `Extends:` line;
- node IDs are generated (`uc1`, `a1`, …), never taken from titles; a `"` in a title or actor name becomes `#quot;`;
- a slug on `Includes:` or `Extends:` that does not exist is left out of the diagram (lint reports it, R3).

No placeholder is added: a project's overridden `srs-capability.html` that keeps `{{use_cases}}` shows the diagram; one without it shows neither. A capability without use cases has no diagram.

### R6. Skill and documentation

- `plugins/gin-workflow/src/skills/sdd/SKILL.md`, discuss step 3: a use case with an alternative or exception flow gets an activity diagram whose `Use case:` line names it, in lanes, with a label on each decision branch; lint rules are not repeated there. The file stays within its 6,000-character budget (`tests/workflow_core/test_token_budget.py`), so existing wording is shortened to make room.
- `docs/guides/sdd.md`, `docs/guides/ba.md`, and their `.vi.md` versions: the new use case lines and sections, lanes, guards, the `Use case:` link, the generated use case diagram, and that technical changes skip the change-level rules.
- `docs/reference/cli.md`: `specs lint` reference checks, the `--against` rules of R4, the technical exemption; `specs export` use case diagram.

## User Stories

### US-1: Write a use case the way a BA does
As a business analyst, I want the use case template to hold the trigger, secondary actors, exception flows, business rules, and include/extend relations, so that a use case reads like the specification in an SRS.

Acceptance criteria:
- `gin specs template use-case.md` prints the lines and sections of R1.
- A use case written from the old template still passes `specs lint`.
- A use case with `Includes: verify-otp` and no `use-cases/verify-otp.md` in its capability fails `specs lint` with the file and slug named.
- A use case whose `Extends:` names itself fails `specs lint`.
- A use case without `Actor:` passes `specs lint` when another use case of its capability includes it, and fails otherwise.

### US-2: See all use cases of a capability at a glance
As a business analyst, I want the SRS to show a use case diagram per capability, so that the customer sees who does what before reading each use case.

Acceptance criteria:
- `gin specs export <cap>` for a capability with two use cases joined by `Includes:`, where only the including one has `Actor:`, prints a `use-case-diagram` section with one `flowchart LR` block holding a subgraph, two use case nodes, one actor node with the `actor` class, one actor edge, and one `«include»` edge.
- An `Extends:` line produces an `«extend»` edge from the extending use case to the extended one.
- `Actor: Customer` and `Actor: customer` in two use cases produce one actor node labelled `Customer`.
- A title containing `"` produces `#quot;` in the block.
- A capability without `use-cases/` has no `use-case-diagram` section.
- An overridden `srs-capability.html` with `{{use_cases}}` shows the diagram.

### US-3: Activity diagrams that show lanes and guards
As a business analyst, I want activity diagrams with lanes, labelled decision branches, and a link to their use case, so that each flow reads like the activity diagram of an SRS.

Acceptance criteria:
- `gin specs template activity.md` prints a `flowchart` block with at least two `subgraph` lanes, every node declared inside a lane, a `((Start))` and an `(((End)))` node, a `{…}` decision, a label on each of its edges, and a `Use case:` line.
- `specs lint --change <epic> --against <base>` exits 1 and names the file and line when a changed activity diagram has an unlabelled edge leaving a decision node, for `-->`, `-.->`, and `==>`.
- The same diagram passes once each such edge has a label in either form (`-->|x|`, `-- x -->`).
- An unchanged activity diagram with an unlabelled decision edge produces no finding.
- An activity diagram whose `Use case:` names a missing use case fails `specs lint`.

### US-4: One diagram per feature, not per capability
As a business analyst, I want lint to stop a change that adds a feature without drawing it, so that every feature has its own activity diagram.

Acceptance criteria:
- With `--against <base>`, a change with an `ADDED` block for a capability that already has an activity diagram, but adds or changes none, fails and names the capability.
- The same change passes once it adds `diagrams/<feature>-activity.md`.
- With `--against <base>`, a change that adds `use-cases/pay.md` with an alternative flow and no activity diagram naming `Use case: pay` fails and names the file; it passes once one does.
- The same change passes without a diagram when `pay.md` has neither an alternative nor an exception flow.
- With `--against <base>`, a change whose delta holds only a `MODIFIED` block needs no changed activity diagram.
- Without `--against`, the existing rule applies unchanged.
- A change whose `01-proposal.md` says `Kind: technical` passes with `ADDED` blocks and no activity diagram, with or without `--against`.

## Errors and compatibility

- Lint findings exit 1, like the other lint findings; `specs archive` stops on them as today.
- Existing projects: use cases and diagrams already on the base branch raise no new finding unless an `Includes:`, `Extends:`, or `Use case:` line names a missing use case; the old template has none of these lines.
- A use case without `Actor:` that another use case includes failed lint before and now passes; no use case that passed before fails now, except for a bad reference.
- A change in flight that adds requirements without changing an activity diagram fails `specs lint --change --against` after upgrading; the message names the template command.
- A `technical` change with a delta that failed the old diagram rule now passes.
- `--against` with a ref git cannot resolve, on a non-technical change: `specs lint --change` exits 2 with `cannot resolve <ref>`, instead of skipping the base checks without a word as `ids_at_ref` does today.
- The SRS of a project with use cases gains a diagram; that output change is intended.
- `dist/` is regenerated by the build; no hand edits there.
