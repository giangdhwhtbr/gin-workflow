# Rename: gin CLI, gin: skill namespace, gin:learn

Epic: gin-workflow-rename-gin
Status: draft for user review.

## Goal and scope

The CLI is `gin-workflow` and the skills, agents, and commands live in the `gin-workflow:` namespace, so a user types `gin-workflow task ready` and `/gin-workflow:discuss`, and several skills repeat the prefix (`gin-workflow:gin-sdd`). This epic makes `gin` the only CLI name and `gin:` the only namespace, and drops the `gin-` prefix from the skills (`gin-knowledge` becomes `learn`).

It is a clean cut: no `gin-workflow` alias is installed. Everything this repository writes into a user's repository under the old name is recognised and rewritten by the new CLI, and `setup doctor` reports what is left on the old name.

In scope:
- the launcher, its install location, and every program name the CLI prints;
- the git hooks, the `AGENTS.md` block, and the `team init` files the CLI writes into user repositories;
- the plugin identity (`gin`) in the marketplace and every harness manifest, and removing old installs;
- the seven skill renames;
- gin-qa and gin-orchestrator calling `gin`;
- one sweep of `plugins/*/src`, `tests/`, `README.md`, `AGENTS.md`, and `docs/` (with the `.vi.md` pages).

Out of scope:
- renaming the repository, the `plugins/gin-workflow/` directory, the gin-qa or gin-orchestrator plugins, or the release archive name;
- the environment variables `GIN_WORKFLOW_*`, the files `.gin-workflow-src.json` and `gin-workflow-bundle.json`, the marketplace id `gin-workflow-marketplace`, the project state folders `.agent-workflow/` and `.planning/`, and the team CI file names `gin-workflow.yml`;
- rewriting history in `.planning/` (specs, plans, knowledge, roadmap);
- gin-console (`collect.py` runs `gin-workflow state`): a bead in the gin-console repository, created at orchestrate, moves it to `gin` after this epic ships;
- `gin-harness/AGENTS.md`, `~/gin-fam/CLAUDE.md`, and other repositories' hand-written files that name `/gin-workflow:*`.

## Requirements

### R1. CLI name

- The launcher is `~/.local/bin/gin` (Windows: `~/.local/bin/gin.cmd`), pointing at `~/.local/lib/gin/<version>/gin`. The source script `plugins/gin-workflow/src/scripts/gin-workflow` is renamed `gin`.
- No `gin-workflow` launcher is installed. `install.sh` and `install.ps1` remove `~/.local/bin/gin-workflow` (`.cmd`) and `~/.local/lib/gin-workflow/` only when the launcher is the managed one (same check as today's `is_managed_launcher_link` / `Test-ManagedLauncherShim`); a foreign file of that name is left and reported.
- Every argparse `prog`, usage line, `--version` line, and message that names the program says `gin` (for example `gin task`, `run gin setup refresh`).

### R2. Files written into user repositories

- Git hooks: the shim calls `gin hooks run <hook>`, its marker is `generated by gin hooks install`, and the missing-CLI message is `gin is not on PATH; run ./install.sh`. `hooks install` treats a hook with the old marker or `gin-workflow hooks run` as its own and rewrites it (`installed`), instead of `chained` or `occupied`. `hooks status` and `setup doctor` report such a hook as `stale` with the fix `gin hooks install`; ship's hook check treats `stale` as not `ok`.
- `AGENTS.md` block: markers `<!-- gin:start ... -->` / `<!-- gin:end -->`, body naming `gin` commands. `setup refresh` finds a block under the old or the new markers and replaces it with the new one; `setup doctor` reports an old-marker block as stale.
- `team init`: the marker becomes `generated by gin team init`, generated files call `gin`, and an existing file with the old marker is rewritten, not refused. The CI file names stay `gin-workflow.yml`.

### R3. Plugin identity

- The plugin name is `gin` in `.claude-plugin/marketplace.json`, `plugins/gin-workflow/src/.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`, and `plugins/gin-workflow/plugin.meta.json`, so skills, agents, and commands are `gin:<name>` in Claude, Codex, and Copilot.
- Install targets follow the name: `~/.claude/skills/gin`, `enabledPlugins["gin@skills-dir"]`, OpenCode `skills/gin` and `agents/gin-*.md`, Codex `gin@gin-workflow-marketplace`, Copilot `gin`, and the Copilot hook fallback path.
- On install, the installers remove the previous `gin-workflow` install for each harness they install into: the Claude skills folder and its `enabledPlugins` key, the OpenCode skills folder and `gin-workflow-*.md` agents, the Copilot plugin, and the Codex plugin, with the same scope (global or project) as the new install. `uninstall` removes both names.
- A user who installed through `claude plugin install gin-workflow@gin-workflow-marketplace` uninstalls `gin-workflow` and installs `gin`; README and the troubleshooting page say so.

### R4. Skill names

- Skill folders: `gin-knowledge` becomes `learn`; `gin-sdd`, `gin-team`, `gin-worktrees`, `gin-debugging`, `gin-review-response`, `gin-parallel-agents` become `sdd`, `team`, `worktrees`, `debugging`, `review-response`, `parallel-agents`. Each `SKILL.md` `name:` matches its folder.
- On OpenCode, where a skill id is its bare folder name, the installers rename these eight skills to `gin-<name>` with a matching `name:` (`gin-learn`, `gin-sdd`, ..., `gin-report`), generalising today's `report` rule; `gin-qa-setup` is unchanged.
- No skill name equals a command name (the existing check in `test_token_budget.py`), and the renamed skills keep the 6,000-character budget that today's `skills/gin-*/SKILL.md` glob gives them.

### R5. gin-qa and gin-orchestrator

- gin-qa (`gin_qa/reqs.py`, `gin_qa/bugs.py`, and the other call sites) and gin-orchestrator (`scripts/gin-orchestrator` facade lookup, `cli.py`, `task_tracking_cli.py`) find and run `gin`. Their "not on PATH" errors name `gin`.
- `executables.py` `KNOWN_TOOLS` lists `gin` instead of `gin-workflow`; an `executables.local.yaml` entry for `gin-workflow` is then reported by the existing `<name>: unknown tool` check, and its message names `gin` as the key to use.
- The orchestrator's worker-agent mapping (`registry.py`) accepts `gin:<agent>` and `gin-<agent>` and maps to the harness form (`gin:<agent>` for Claude, `gin-<agent>` for OpenCode). The orchestrator's task-tracking provider id stays `gin-workflow`, an internal id not shown as a command.
- The installers' gin-qa check and gin-orchestrator dependency on the CLI test for `gin`.

### R6. Sweep

- `plugins/*/src`, `tests/`, `README.md`, `AGENTS.md`, `docs/` (English and `.vi.md`) use `gin` for every CLI invocation, `gin:` for every skill, agent, and command reference, and the new skill names. Anchors that carry the old name (for example `#gin-workflow-command-not-found-after-a-marketplace-install`) are renamed with their links.
- A test fails when `gin-workflow ` used as a command or `gin-workflow:` appears in those paths, except an allow list: `plugins/gin-workflow/` paths, `GIN_WORKFLOW_*`, `gin-workflow-marketplace`, `.gin-workflow-src.json`, `gin-workflow-bundle.json`, `gin-workflow.yml`, the orchestrator provider id, the old markers kept for migration (R2), the old install paths removed by R1 and R3, and the upgrade notes that name the old command.

## User Stories

### US-1: Type gin
As a developer, I want to run `gin task ready` and `/gin:discuss`, so that the commands I type every day are short.

Acceptance criteria:
- After `./install.sh`, `gin --version` prints `gin <version>`, and `command -v gin-workflow` finds nothing when the old launcher was the managed one.
- `gin <sub> --help` shows `usage: gin <sub>`.
- In Claude Code, the skills appear as `gin:discuss`, `gin:learn`, `gin:sdd`; no `gin-workflow:` skill remains after reinstall.

### US-2: Existing repositories keep working after one command
As a developer upgrading, I want my repositories' hooks and `AGENTS.md` moved to the new name by the CLI, so that I do not edit generated files by hand.

Acceptance criteria:
- In a repository with old hooks, `gin setup doctor` reports the hooks as stale with `gin hooks install`; after it, `gin hooks status` shows `ok` and a commit runs `gin hooks run pre-commit`.
- In a repository with an old `<!-- gin-workflow:start -->` block, `gin setup refresh` leaves exactly one block, with the `gin:` markers.
- `gin team init` rewrites its old-marker files instead of refusing them.

### US-3: One install, no duplicates
As a developer, I want the installer to remove the old `gin-workflow` plugin when it installs `gin`, so that no harness shows each skill twice.

Acceptance criteria:
- After `./install.sh` over a 2.2.0 install, `~/.claude/skills/gin-workflow` and `enabledPlugins["gin-workflow@skills-dir"]` are gone, and `~/.claude/skills/gin` exists.
- The OpenCode, Copilot, and Codex installs hold only `gin`.
- `./install.sh uninstall` removes both names.

### US-4: The add-ons follow
As a QA or orchestrator user, I want gin-qa and gin-orchestrator to call `gin`, so that they work on a machine with only `gin` on PATH.

Acceptance criteria:
- With only `gin` on PATH, `gin-qa` requirement lookup and `gin-orchestrator dispatch` succeed.
- Dispatching a worker agent named `gin:developer` resolves on Claude and on OpenCode.

## Errors and compatibility

- Clean cut: scripts, CI jobs, and repositories that call `gin-workflow` fail with "command not found" until updated. A hook installed before the upgrade fails the commit with `gin-workflow is not on PATH; run ./install.sh`, so no check is skipped silently; `gin hooks install` fixes it.
- gin-console fails to read project state from the time this epic ships until its bead is done.
- Team CI that installs the CLI from `GIN_WORKFLOW_INSTALL` keeps working; generated CI files call `gin` once `gin team init` rewrites them.
- Upgrading does not migrate a marketplace install of `gin-workflow`; the user reinstalls (R3).
- Assumptions: the BA epics (`gin-workflow-ba-plugin`, `gin-workflow-explain`) are discussed after this ships and use the new names, so the sweep runs once; the version becomes 3.0.0 because the CLI and namespace change incompatibly.

## Testing

- Unit: hooks install, status, and doctor with an old-marker hook; `setup refresh` with an old-marker `AGENTS.md` block (one block left); `team init` with old-marker files; `prog` of each subcommand starts with `gin`; orchestrator agent mapping for `gin:` names; `KNOWN_TOOLS` and the `gin-workflow: unknown tool` message.
- Existing tests that name `gin-workflow:`, the `gin-*` skill paths, or the `skills/gin-*/SKILL.md` budget glob are updated, not deleted.
- Installer smoke tests (`tests/install_smoke_test.sh`, `.ps1`): the `gin` launcher exists, a managed `gin-workflow` launcher and `~/.claude/skills/gin-workflow` are removed, a foreign `gin-workflow` file is kept, and OpenCode gets the eight `gin-<name>` skill ids.
- The sweep test of R6.
- `gin docs check` and `mkdocs build --strict` pass.
