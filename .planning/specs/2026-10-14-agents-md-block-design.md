# AGENTS.md Managed Block — Design

Status: draft for user review.

## Goal and scope

Give every harness (Claude, Codex, Antigravity, opencode) the same short project context without a new skill or a new lifecycle step. `gin-workflow setup` renders a managed block in `AGENTS.md`, and `CLAUDE.md` imports it with `@AGENTS.md`. The block holds only facts the repository already records: the workflow, the configured checks, and links to the roadmap and codebase docs that exist.

The block is written only by the setup CLI (`init`, `refresh`), never by an agent or another stage, so it has one owner and renders the same on every machine.

Out of scope:
- A `/gin-workflow:init` skill or a call to Claude's `/init`.
- Copying rule-pack bullets, product summaries, or conventions into the block; agents fetch rules with `gin-workflow rules --files`, and conventions grow in `.agent-workflow/rules/*.md` and `bd remember`.
- A config key to disable the block; deleting the block disables it.

## Requirements

### Rendering
The block is rendered from tracked data only: `.agent-workflow/config.yaml` and whether the roadmap and codebase-doc paths exist.

```markdown
<!-- gin-workflow:start — generated by `gin-workflow setup refresh`; edit outside this block -->
## gin-workflow

- Track work in Beads (`bd`). Stages: `/discuss` → `/plan` → `/orchestrate` → `/execute` → `/ship`; `/workflow` runs the next one; small changes: `/quick`.
- Never commit to `main`/`master`. Opening a PR, merging, or force-pushing needs user approval.
- Before editing code, run `gin-workflow rules --files <paths>` and follow its output.
- Checks (git hooks): lint `<cmd>` · typecheck `<cmd>` · test `<cmd>` · build `<cmd>` · e2e `<cmd>`
- Roadmap: `<roadmap path>` · Codebase docs: `<codebase path>`
<!-- gin-workflow:end -->
```

- Checks: only non-empty `verify.checks` entries, in the order lint, typecheck, test, build, e2e. With none: `- Checks: none configured yet; \`gin-workflow setup doctor\` reports them once sources exist.`
- Docs line: each link only when its path exists. Legacy layout: `.planning/roadmap.md`, `.planning/codebase/`. SDD layout: `docs/roadmap.md`, `artifacts.codebase` (default `docs/codebase/`). Neither exists: the line is dropped.
- No CodeGraph line (`.codegraph/` is usually gitignored, so it would differ per machine) and no harness-specific line.
- The block is English, like other tracked content.

### Commands
- `setup init`: creates `AGENTS.md` if missing; inserts or replaces the block (appended at the end when the file has none). Creates `CLAUDE.md` with `@AGENTS.md` if missing; prepends `@AGENTS.md` to an existing `CLAUDE.md` that has no such line. Both appear in `actions`; `--dry-run` writes nothing.
- `setup refresh`: replaces the block only when it already exists; otherwise reports `agents_block: absent` and writes nothing to `AGENTS.md`. Never touches `CLAUDE.md`.
- `setup doctor`: reports `agents_block` as `ok`, `stale` (differs from a fresh render; action: run `gin-workflow setup refresh`), `absent` (not an error), or `invalid`.
- Content outside the markers is preserved byte for byte, including line endings. Writes are atomic (temp file, then replace).

### Skills
- `/roadmap` and `/tech-doc` add to their report step: run `gin-workflow setup refresh` to update the links in `AGENTS.md`.

## User Stories

### US-1: Shared context for every harness
As a developer starting a new project, I want `/setup` to give every agent the workflow rules and checks, so that a session in any harness follows the same process from the first task.

Acceptance criteria:
- After `setup init` on an empty repository, `AGENTS.md` contains the block and `CLAUDE.md` contains `@AGENTS.md`.
- After `setup init` on a repository with its own `AGENTS.md` and `CLAUDE.md`, all content outside the block is unchanged.
- The checks line lists exactly the configured non-empty `verify.checks`.

### US-2: Context grows with the project
As a developer on a greenfield project, I want the block to pick up the roadmap, codebase docs, and checks once they exist, so that it never states something not yet decided.

Acceptance criteria:
- On a greenfield repository with no checks, the block says checks are not configured yet and has no docs line.
- After the roadmap file is written, `setup refresh` adds its link; `setup doctor` reported `stale` before the refresh.
- `/roadmap` and `/tech-doc` reports tell the user to run `gin-workflow setup refresh`.

### US-3: The user stays in control
As a developer, I want to edit around the block or remove it, so that gin-workflow never overrides what I wrote.

Acceptance criteria:
- After the block is deleted, `setup refresh` does not recreate it and `setup doctor` reports `absent` without failing.
- A second `init` or `refresh` with no change in inputs produces no diff.

## Errors and compatibility

- Broken markers (missing end, duplicated start or end, end before start): `init` and `refresh` raise `SetupError` and leave the file unchanged; `doctor` reports `invalid`.
- An existing repository gets the block only by running `setup init` again (idempotent) or by adding the markers by hand and running `refresh`; no migration and no schema version bump.
- `rules_checks` keeps treating `CLAUDE.md` and `AGENTS.md` as conflict sources; the block holds no rule bullets, so it adds no conflicts.

## Testing

- Render: each variant — with and without checks, with and without roadmap and codebase docs, legacy and SDD layout.
- `init` on an empty repository creates both files; on existing files, bytes outside the block are unchanged (LF and CRLF).
- Idempotence: a second `init` or `refresh` leaves both files byte-identical.
- `refresh` adds the roadmap link after the file appears; does not recreate a deleted block.
- Broken markers: error, file unchanged.
- `doctor`: `ok`, `stale`, `absent`, `invalid`.
- Packaging: the installed `roadmap` and `tech-doc` skills contain the refresh reminder.
- Docs: `docs/reference/cli.md` (`init`, `refresh`, `doctor`) and `docs/reference/config.md` describe the block.
