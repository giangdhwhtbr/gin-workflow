# Plan: write-doc skill and docs check command

Workflow: write-doc
Spec: .planning/specs/2026-10-30-write-doc-design.md

## Objective
A team member who asks for a README, runbook or guide, ADR, or changelog gets it from one skill, `write-doc`, built from a fixed template and accepted only when `gin-workflow docs check` exits 0.

## Goal, architecture, tech stack

- Goal: stable standalone documents across team members, from one plugin (spec, "Goal and scope").
- Architecture: one skill file (instructions), three Markdown templates resolved by the existing `specs.template_text`, and one CLI module `workflow_core/docs_check.py` dispatched from `workflow_core/cli.py` like `specs`. The mechanical style rules move from `tests/workflow_core/test_docs_coverage.py` into that module, so the test and the command share one definition.
- Tech stack: Python 3 standard library (`argparse`, `re`, `json`, `pathlib`), `unittest`, Markdown.

## Global Constraints

Copied from the spec:
- The skill never records a gate, never creates a Beads task, never stops for `/setup`, and commits only when the user asks.
- The command reads no workflow configuration, so it runs in a repository without `.agent-workflow/`.
- Exit 0 when no findings, 1 when findings, 2 when a file does not exist or the template is unknown (message on stderr).
- `STYLE_RULES` and `style_violations` move into `docs_check.py` unchanged, and the test imports them from there.
- The skill description stays at or under 350 characters.
- Version bumps of the CLI or launcher happen at release, per `docs/contributing.md`; not in this plan.
- Uninstalling technical-writer is a team convention; no code enforces it.

Repository rules: commit only on `feat/write-doc-skill`, never on `master`. Test command for every track: `PYTHONPATH=plugins/gin-workflow/src/scripts python3 -m unittest <file>`; full suite `PYTHONPATH=plugins/gin-workflow/src/scripts python3 -m unittest tests/test_all.py`.

## Route Rubric
- Choose the weakest model that can do the work.
- Raise the model for broad context or design judgement.
- Raise the effort for intrinsic difficulty: intricate logic, many edge cases, or long chains of steps.

| Kind of work | Model | Effort |
|---|---|---|
| Mechanical edits, documentation, boilerplate | weakest | `low` |
| Bounded implementation with a clear spec | middle | `medium` |
| Cross-module change, security, migration, concurrency | strongest | `high` |

Unclear requirements never raise the model or effort.

## Requirement Analysis
- Problem statement: standalone documents (README, runbook, ADR, changelog) have no entry point in gin-workflow, so each member writes them in a different shape, and "done" depends on who ran the agent.
- Success criteria: spec user stories US-1 to US-5; the full suite and the install smoke test pass.
- Constraints: Global Constraints above.
- Non-goals: legacy migration inventory (spec Follow-up), reviewer agent, specs and plans, codebase docs, issues, version bumps.

## Approach Options
### Option 1: One skill, fixed templates, a machine check (selected)
- Summary: `write-doc` picks a template per type; `gin-workflow docs check` is the done criterion.
- Pros: same result for every member; one skill; reuses `specs.template_text` and the existing style rules.
- Cons: a new top-level CLI command to document and maintain.

### Option 2: One skill, templates, self-review only
- Summary: as option 1 without the command.
- Pros: no CLI change.
- Cons: an LLM read-through finds different issues on each run, which is the instability the spec removes.

### Recommended Approach
- Selected option: 1, confirmed by the user in `/discuss` on 2026-10-30.

"""`gin-workflow docs check`: mechanical rules for Markdown pages. Exit 0 ok, 1 findings, 2 usage error."""

from __future__ import annotations

import argparse
import json
from pathlib import Path
import re
import sys
from typing import Iterator, Sequence

from . import specs

STYLE_RULES = (("dash", re.compile("[–—]")),
               ("bold-label item", re.compile(r"^\s*(?:[-*+]|\d+[.)])\s+\*\*")),
               ("emoji", re.compile("[\U0001F300-\U0001FAFF☀-➿⭐⭕️]")),
               ("numbered heading", re.compile(r"^#{1,6}\s+\d")))
PLACEHOLDER = re.compile(r"\{\{[^}]*\}\}|\b(?:TBD|TODO)\b")
INLINE_CODE = re.compile(r"`[^`]*`")
LINK = re.compile(r"\]\(([^)\s]+)\)")


def _prose(text: str) -> Iterator[tuple[int, str]]:
    """Numbered lines outside fenced code blocks."""
    fenced = False
    for number, line in enumerate(text.splitlines(), 1):
        if line.lstrip().startswith("```"):
            fenced = not fenced
            continue
        if not fenced:
            yield number, line


def style_violations(text: str) -> list[str]:
    """Mechanical docs-pack rules outside fenced code blocks, as '<line>: <rule>'."""
    return [f"{number}: {name}" for number, line in _prose(text) for name, pattern in STYLE_RULES
            if pattern.search(line)]


def required_sections(repository: Path, template: str) -> list[str]:
    """Literal '## ' headings of a template; a heading with a placeholder varies per page and is skipped."""
    return [line.rstrip() for line in specs.template_text(repository, template).splitlines()
            if line.startswith("## ") and "{{" not in line]


def page_findings(page: Path, text: str, required: Sequence[str] = ()) -> list[str]:
    """Every rule for one page, ordered by line; missing sections last."""
    found = []
    for number, line in _prose(text):
        prose = INLINE_CODE.sub("", line)
        found += [f"{page}:{number}: {name}" for name, pattern in STYLE_RULES if pattern.search(line)]
        if PLACEHOLDER.search(prose):
            found.append(f"{page}:{number}: placeholder")
        for target in LINK.findall(prose):
            path = target.split("#", 1)[0]
            if path and not re.match(r"[a-z]+:", path) and not (page.parent / path).exists():
                found.append(f"{page}:{number}: dead link")
    lines = {line.rstrip() for line in text.splitlines()}
    return found + [f"{page}: missing section: {heading}" for heading in required if heading not in lines]


def _parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="gin-workflow docs")
    sub = parser.add_subparsers(dest="command", required=True)
    check = sub.add_parser("check")
    check.add_argument("files", nargs="+", type=Path)
    check.add_argument("--template")
    check.add_argument("--repository", type=Path, default=Path.cwd())
    check.add_argument("--format", choices=("text", "json"), default="text")
    return parser


def main(arguments: Sequence[str] | None = None) -> int:
    args = _parser().parse_args(arguments)
    missing = [str(path) for path in args.files if not path.is_file()]
    if missing:
        print(f"no such file: {', '.join(missing)}", file=sys.stderr)
        return 2
    try:
        required = required_sections(args.repository.resolve(), args.template) if args.template else []
    except specs.SpecsError as error:
        print(error, file=sys.stderr)
        return 2
    found = [item for path in args.files
             for item in page_findings(path, path.read_text(encoding="utf-8"), required)]
    if args.format == "json":
        print(json.dumps({"status": "findings" if found else "ok", "findings": found}, indent=2, sort_keys=True))
    else:
        print("\n".join(found) if found else "ok")
    return 1 if found else 0
````

# Write Doc

Write or update one standalone document so that every team member gets the same structure and the same checks. This skill sits outside the lifecycle: it never records a gate, never creates a Beads task, never stops for `/setup`, and commits only when the user asks.

## Document types

| Type | Template | Default target |
|---|---|---|
| README | `readme.md` | `README.md` in the repository or module root |
| Runbook or guide (setup, procedure, troubleshooting, migration guide) | `runbook.md` | `docs/runbooks/<slug>.md` |
| ADR | `adr.md` | `artifacts.adr` from `.agent-workflow/config.yaml`, default `docs/adr`; file `NNNN-<slug>.md` with the next free number |
| Changelog or release notes | `changelog.md` | `CHANGELOG.md` in the repository root; a new entry goes above the previous ones |
| Other | none | the path the user gives |

## Steps

1. Classify the request: document type, target path, and new file or update. Ask one question only when the type or the target cannot be inferred. A request that describes a shape outside the table is written without a template, under the same rules.
2. Gather evidence from the code, configuration, and scripts the document describes: `codegraph explore "<question>"` when `.codegraph/` exists, otherwise grep and read. Check every command, path, flag, and default the document states against the repository.
3. Load the template with `gin-workflow specs template <name>`, the rules with `gin-workflow rules --files <target>`, and [references/docs-style.md](../../references/docs-style.md).
4. Write. A new file starts from the template; fill every placeholder. In an existing file, change only the sections the request names and leave every other line unchanged; restructure the file only when the request asks for it.
5. Run `gin-workflow docs check <target>`, adding `--template <name>` for a new file, and fix every finding until it exits 0. Then read the page once against `docs-style.md` for what the command cannot check, first of all that each claim matches the code.
6. Report: the file written, the sections changed, the evidence files, the commands checked against the repository and those that were not, and the `docs check` output.

When a template is unknown, `docs check` exits 2: stop and name the template instead of inventing its structure.
