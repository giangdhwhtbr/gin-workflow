# Plan: write-doc skill

Workflow: write-doc
Spec: .planning/specs/2026-10-30-write-doc-design.md

## Objective
Add a general-purpose skill `write-doc` that writes or updates README, runbook, setup guide, and ADR documents, outside the lifecycle, with the same template and style rules as the rest of gin-workflow.

## Global Constraints
- No workflow state, Beads task, or gate in the skill. It works without `.agent-workflow/generated/effective-config.yaml`.
- Style rules come from `plugins/gin-workflow/src/references/docs-style.md`. Do not add a second style file.
- Templates load through `gin-workflow specs template <name>`, so `.agent-workflow/templates/` overrides keep working.
- The skill is discovered by its folder under `plugins/gin-workflow/src/skills/`. No manifest edit.
- Do not change `tech-doc` output or the CLI.
- Commit only on `feat/write-doc-skill`. Never commit to `master`.

## Route Rubric
Route choices in the tracks below follow the rubric in `plan-schema.md`.

## Requirement Analysis
- Problem statement: teams write README, runbook, and ADR pages by hand, and the shapes drift between members.
- Success criteria: each listed type has a template; `write-doc` is registered and documented; the tests pass.
- Constraints: Global Constraints above.
- Non-goals: legacy analysis (sub-project B), reviewer agent, state gates.

## Approach Options
### Option 1: One skill that picks a template per type (chosen)
- Summary: one SKILL.md with a type table; templates in `src/templates/`.
- Pros: one new skill, reuses template and rule mechanisms.
- Cons: the skill file carries branch logic.

### Option 2: One skill per document type
- Summary: `write-readme`, `write-runbook`, `write-adr`.
- Pros: each file is simple.
- Cons: three new skills, against the team request for one.

### Recommended Approach
- Selected option: 1.
- Rationale: the spec asks for one skill, and the template mechanism already exists.

## Scope
- In scope: two new templates, one new skill, one reference row, tests.
- Out of scope: everything listed in the spec's Goal and scope.

- **Effort:** `medium`
- **Why:** two templates with a clear shape and a test that proves they load through `specs template` and accept overrides. Middle model because the test must match how `specs.py` resolves templates.

- **Acceptance criteria**:
  - `gin-workflow specs template readme.md` and `runbook.md` print the new templates.
  - A file at `.agent-workflow/templates/runbook.md` in a fixture repo replaces the plugin template.
  - Each template has `{{title}}` and no placeholder text outside the braces (no TBD or TODO).
- **Estimated complexity**: low

Steps:
1. Find how the existing template test drives `specs.template_text` in `tests/workflow_core/test_specs.py` (lines 140-220). Run `python3 -m unittest discover -s tests/workflow_core -p "test_specs.py"` once to confirm the command works. Expected: `OK`.

6. Commit: `feat(write-doc): add readme and runbook templates`.
