# Plan: Codebase glossary for legacy migrations

Spec: `.planning/specs/2026-11-05-codebase-glossary-design.md`
Workflow: codebase-glossary

## Objective

`/tech-doc` collects the business terms of a non-English legacy system into one `11-GLOSSARY.md` per repository (monorepo root), with a proposed English term and a citation per row, and keeps confirmed terms across runs. A `glossary` rule pack, `discuss`, and `plan` make specs, plans, code, and reviews of the new application use the confirmed terms. Docs describe the flow.

Goal, architecture, and constraints from the spec (verbatim):

- Goal: every epic of the new application names the same business concept with the same English term.
- Architecture: an eleventh page in the tech-doc set, `11-GLOSSARY.md`, collected by the existing scouts and merged across runs into one file for the whole monorepo; a plugin rule pack `glossary` that makes developers and reviewers use the confirmed English terms; one line each in `discuss` and `plan` so specs and plans use the same terms.
- Tech stack: Markdown skill and template files, a Markdown rule pack with YAML frontmatter, Python `unittest` tests run with pytest.
- Global constraints:
  - A `confirmed` row's `English` never changes.
  - Enabling the pack is opt-in (`rules.packs`).
  - Each stage stays within the 12,000-character stage budget.
  - Numbers 01 to 10 of the tech-doc set do not change.

## Requirement Analysis
- Problem statement: no gin-workflow stage collects or enforces terms; tech-doc pages are not read by later stages (`skills/tech-doc/SKILL.md`, intro), so a glossary needs both a producer and consumers.
- Success criteria: the user stories US-1 to US-3 of the spec, checked by the tests named in each track, `gin-workflow docs check`, `mkdocs build --strict`, and the full suite.
- Constraints: the global constraints above; plugin packs must keep the rule-pack lint (`tests/workflow_core/test_rule_packs.py`) green.
- Non-goals: a `/glossary` skill, a YAML or CSV copy, a CLI to confirm terms, a code-identifier column, automatic enabling, version bumps.

## Approach Options
### Option 1: Producer and consumers in two tracks
- Summary: Track 1 adds the template, the tech-doc skill text, and the docs that describe the tech-doc set. Track 2 adds the rule pack, the `discuss` and `plan` lines, and the rule-pack docs.
- Pros: each track has its own test cycle and file set; no file is touched by both; either can be rejected alone.
- Cons: the brownfield walkthrough (Track 1) mentions `rules.packs: [glossary]`, which exists only after Track 2; harmless for tests, and both merge before ship.

### Option 2: One track
- Summary: every change in one track.
- Pros: one review.
- Cons: a reviewer cannot reject the rule pack without the tech-doc change; a larger diff for one review.

### Recommended Approach
- Selected option: Option 1.
- Rationale: two independent, small units, the size a reviewer can reject separately.

## Scope
- In scope: spec R1 to R5.
- Out of scope: the spec's out-of-scope list. R5's "rebuild `dist/`" needs no step: `dist/` is generated by the installer and not tracked (`docs/contributing.md:23`); the harness packaging tests build into temporary homes, and the installed plugin is refreshed by `./install.sh` after the merge.
- Deliberate test change: `test_core_and_lean_apply_everywhere_and_others_are_scoped` (`tests/workflow_core/test_rule_packs.py`) forbids `**/*` for packs other than `core` and `lean`. `glossary` is exempted by name, because it applies to every language of the new application and loads only when a project lists it in `rules.packs`.
