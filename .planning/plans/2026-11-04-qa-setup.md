# Plan: gin-qa project setup

Epic: gin-workflow-qa-setup
Spec: .planning/specs/2026-11-04-qa-setup-design.md

## Objective

`/gin-qa:setup` interviews a project once and writes `qa/guidelines.md`, `qa/README.md`, and `.claude/skills/<name>-qa/SKILL.md`. In a project that already has these files, it adds only what is missing and shows each change first. It ends with `gin-qa cases check` exiting 0. `cases check` gains a `## Types` rule, `/gin-qa:cases` and `/gin-qa:run` read the new guidelines sections, and the OpenCode bundle names the skill `gin-qa-setup` so it does not shadow gin-workflow's `setup`.

Goal (from the spec): A project gets its QA rules and process from one interview: `/gin-qa:setup` writes `qa/guidelines.md`, `qa/README.md`, and a thin project-local skill, and leaves them passing `gin-qa cases check`. A project that already has these files gets the missing parts added and the managed parts updated, never overwritten.

Architecture:
- `plugins/gin-qa/src/scripts/gin_qa/cases.py` gains `declared_types(root, guidelines)`, which parses `## Types`. `cli.py` `_check` reports its findings and each case whose type is not listed, before the legacy layout returns.
- Templates:
  - `templates/guidelines.md` gains `## Types`, `## Manual runs`, and `## Bugs`.
  - `templates/qa-readme.md` gains `## Process`.
  - The new `templates/project-skill.md` is the project skill, with `{{name}}`, `{{guidelines}}`, and `{{readme}}` placeholders.
- The new skill `skills/setup/SKILL.md` runs the interview and the writes; the agent edits the files, and no CLI command writes them.
- `skills/cases/SKILL.md` and `skills/run/SKILL.md` read the new sections. The `e2e` description is shortened to keep the plugin within the 1,000-character description budget: it is 966 today, and adding `setup` brings it to 992.
- `install.sh` and `install.ps1` rename gin-qa's OpenCode `skills/setup` to `skills/gin-qa-setup`.

Tech Stack:
- Python 3 stdlib (`re`, `pathlib`) in the gin-qa CLI.
- Tests are `unittest` tests, run with `python3 -m pytest -n auto`.
- Installers are bash and PowerShell. Skills, templates, and docs are Markdown.

### Global Constraints (verbatim from the spec)

- Out of scope: generating the project skill for harnesses other than Claude Code (`docs/guides/qa.md` says where to copy it); running `gin-qa e2e init` (`/gin-qa:e2e` already runs it on first use); a `gin-qa setup` CLI command; syncing bugs to an external tracker; the existing OpenCode clash where gin-qa's `report` is also renamed `gin-workflow-report` (reported, not fixed here).
- `cases check` keeps its exit codes: 0 ok, 1 findings, 2 usage or environment error. The `## Types` rule only adds findings, and only when the section exists, so current projects (gin-console has no `## Types`) keep passing.
- `cases export`, `e2e export`, `tests` output, and `report` are unchanged, so gin-console is not affected.
- Setup never writes a managed part without confirmation and never edits case files; a check finding in an existing case is reported, not fixed.
- The project skill holds process only; when plugin behavior changes, it still points to the plugin skills and CLI rather than to copied rules. That limits drift but does not prevent it: rerunning `/gin-qa:setup` shows the difference against the current template.
- gin-qa `VERSION` becomes `0.10` and the plugin `0.11.0`.

## Requirement Analysis
- Problem statement:
  - The only machine-read guidelines section is `## Automated types` (`tests.py:22`, `declared` at `tests.py:56-98`). Nothing lists the case types, so a misspelled suffix such as `.ap.md` passes `cases check` (`cli.py:121-142`).
  - The template guidelines (`templates/guidelines.md`) have no sections for manual runs or bugs. `/gin-qa:run` hard-codes `manual <YYYY-MM-DD>` and treats the external reference as optional (`skills/run/SKILL.md`, steps 3 and 4).
  - Nothing writes a project's QA files from an interview. `/gin-qa:cases` copies the templates unchanged on first use (`skills/cases/SKILL.md`, step 3).
  - There is no project-local skill mechanism; `install.sh` installs skills per user (`install.sh:668,682`).
  - OpenCode selects a skill by its directory id. A gin-qa `skills/setup` directory would shadow gin-workflow's `setup`, the way `report` is renamed today (`install.sh:567-573`, `install.ps1:313-330`).
- Facts checked while planning:
  - `cases._lines` splits on `\n` only (`cases.py:110-112`), so a CRLF guidelines line ends in `\r`; the parser strips each line before matching.
  - `description_chars` sums the raw `description:` values of `skills/*/SKILL.md`, `agents/*.md`, and `commands/*.md`, quotes included (`workflow_core/budget.py:17,69-77`). gin-qa is at 966 today; the e2e value is 256 characters with its quotes.
  - The template's `## Automated types` example is indented by four spaces, so neither `declared` nor a `- ` line rule reads it.
  - `plugins/*/dist/` is generated by the installer and not tracked (`docs/contributing.md:23`), so no dist file is committed.
- Success criteria: the spec's US-1 to US-5 acceptance criteria; `python3 -m pytest -n auto` passes; `bash tests/install_smoke_test.sh` passes.
- Constraints: Global Constraints above.
- Non-goals: Out of scope above.

## Approach Options
### Option 1: Skill-driven setup, one CLI rule
- Summary: the agent writes the files from the templates under the skill's rules. The CLI only gains the `## Types` check.
- Pros: little code; the same pattern `/gin-qa:cases` and `/gin-qa:tests` already use to create and extend the guidelines.
- Cons: the writes are only as exact as the agent following the skill. The final `cases check` and `tests check` catch structural mistakes.

### Option 2: `gin-qa setup --answers <json>` writes the files
- Summary: a CLI command merges answers into the Markdown sections.
- Pros: the writes are deterministic.
- Cons: a section-merging writer for Markdown is the most error-prone part, it runs once per project, and the spec puts it out of scope.

### Recommended Approach
- Selected option: Option 1.
- Rationale: confirmed in `/discuss`; it matches the existing skills and keeps the CLI change to one rule.

```python
def declared_types(root: Path, guidelines: str) -> tuple[set[str] | None, list[str]]:
    """The types listed under `## Types` in the guidelines, or None without the file or section; and its findings."""
    path = root / guidelines
    if not path.is_file():
        return None, []
    lines = [line.rstrip() for line in _lines(path)]
    start = next((index for index, line in enumerate(lines) if line == TYPES_SECTION), None)
    if start is None:
        return None, []
    types: set[str] = set()
    errors: list[str] = []
    for index in range(start + 1, len(lines)):
        line = lines[index]
        if line.startswith("## "):
            break
        if not line.startswith("- "):
            continue
        entry = _TYPE_ENTRY.match(line)
        if entry:
            types.add(entry.group(1))
        else:
            errors.append(f"{guidelines}:{index + 1}: '{TYPES_SECTION}' entry is not \"- `<type>`: <description>\"")
    if not types and not errors:
        errors.append(f"{guidelines}:{start + 1}: '{TYPES_SECTION}' lists no types")
    return types, errors
```
