# Plan: gin-ba plugin: mockup and legacy capture skills

Epic: gin-workflow-ba-plugin
Spec: .planning/specs/2026-11-06-ba-plugin-design.md

## Objective
A BA prepares a capability's inputs with two skills of a new add-on `gin-ba`: `gin-ba:mockup` writes a self-contained interactive HTML mockup in a dated asset folder, `gin-ba:capture` describes a legacy feature from screenshots there, and each marks its folder `Confirmed: <date>` after the BA confirms. SDD discuss reads only confirmed inputs and cites them per requirement with a `Source:` line. `install.sh`/`install.ps1` install `gin-ba` without a launcher.

Architecture: no Python code. Core gains one template line (`Confirmed: no`), one template comment (`Source:`), and one sentence in the `sdd` skill. A new plugin tree `plugins/gin-ba/` holds three manifests, two skills, and one reference file per skill. The installers get the plugin name, a shared "gin missing" warning, and a launcher-free branch. Docs add the BA guide and reference entries.

Tech stack: Markdown skills, Bash and PowerShell installers, Python 3 `unittest` tests run by `python3 -m pytest -n auto`, `tests/install_smoke_test.sh` and `tests/install_smoke_test.ps1`.

Global Constraints (from the spec):
- Core files never name `gin-ba` (`plugins/gin-workflow/src`); they describe the artifacts only.
- SDD layout only: both skills stop with the legacy layout.
- A confirmed dated folder is frozen; a later round of inputs gets a new dated folder.
- No BA CLI, no `specs assets new`, no `gin-ba:change`, no Figma import, no lint for `Confirmed:`, `Source:`, or mockup size.
- `gin-ba` installs no launcher: nothing under `~/.local/bin/gin-ba` or `~/.local/lib/gin-ba/`; the add-on refresh loop stays limited to add-ons with a launcher.
- Each skill at most 6,000 characters; the plugin's skill descriptions at most 1,000 characters; `sdd/SKILL.md` stays within 6,000 (5,332 today).
- Every docs page follows `plugins/gin-workflow/src/references/docs-style.md` (no em or en dashes).

## Approach Options
### Option 1: Skills-only add-on plus a small core change (chosen in discuss)
- Summary: plugin `gin-ba` with two skills and references, `Confirmed:`/`Source:` conventions in core templates and the `sdd` skill, installer branch without a launcher.
- Pros: no new code path to maintain; reuses `gin specs template` and the dated-folder lint.
- Cons: the agent creates the folder by hand; nothing lints `Confirmed:` or `Source:`.

### Option 2: Option 1 plus a `gin-ba` CLI
- Summary: a launcher with `gin-ba assets new|confirm`.
- Pros: deterministic folder creation and confirmation.
- Cons: a launcher, a library copy, a refresh path, and tests for what is a `mkdir`, a template, and one line edit.

### Recommended Approach
- Selected option: Option 1.
- Rationale: chosen by the user in discuss on 2026-11-06 (spec R1, R2, and "Out of scope").

   ````markdown
   # BA add-on (`gin-ba`)

   `gin-ba` is an optional plugin with two skills that prepare a capability's inputs before `/gin:discuss` writes requirements: `/gin-ba:capture` describes an existing feature from screenshots, and `/gin-ba:mockup` builds an interactive HTML mockup. Both write into the dated asset folders of the [SDD layout](sdd.md) and need gin-workflow. The plugin has no CLI and is not installed by default.

   ```mermaid
   flowchart LR
     A["Screenshots in<br/>assets/date/legacy/"] --> B["/gin-ba:capture<br/>description.md"]
     B --> C["/gin-ba:mockup<br/>mockup/index.html"]
     C --> D["BA confirms<br/>Confirmed: date"]
     D --> E["/gin:discuss<br/>Source: lines"]
     E --> F["diagrams, archive,<br/>specs export"]
   ```

   ## Install

   From a clone of this repository, or remotely:

   ```bash
   ./install.sh --plugin gin-ba          # or --plugin all for every plugin
   curl -sSL https://raw.githubusercontent.com/giangdhwhtbr/gin-workflow/master/remote-install.sh | bash -s -- --plugin gin-ba
   ```

   This installs the skills for each harness. `gin-ba` has no launcher; the installer warns when `gin` is missing.

   ## Dated folders

   Each round of inputs for a capability lives in `docs/specs/<capability>/assets/<YYYY-MM-DD>/`, named by the day the inputs arrived, with a `description.md` from `gin specs template iteration.md`. Both skills take the capability and `--date YYYY-MM-DD` (default: today):

   - A missing folder is created with its `description.md`; `Previous:` names the latest earlier dated folder.
   - A folder whose `description.md` reads `Confirmed: <date>` is frozen: the skill stops and asks for a new date.
   - An unconfirmed folder is continued.

   The skills set `Confirmed: <today>` only after the BA explicitly confirms, and never commit: the BA reviews and commits the folder.

   ## Legacy capture: `/gin-ba:capture`

   1. Put the screenshots of the existing feature under `docs/specs/<capability>/assets/<date>/legacy/` (`.png`, `.jpg`, `.jpeg`, `.webp`, or `.gif`).
   2. Run `/gin-ba:capture <capability> --date <date>`, optionally followed by code paths that show the feature's checks. The skill reads only the paths you name.
   3. Review `description.md`: `Kind: legacy`, one `### <Screen>` per screen with a `Field | Type | Required | Rule` table and its actions, `## Rules`, and `## Open questions`. A value the evidence does not settle reads `?` and has an open question.
   4. Confirm it; the skill sets `Confirmed: <today>`.

   ## Mockup: `/gin-ba:mockup`

   `/gin-ba:mockup <capability>` writes `assets/<date>/mockup/index.html`, one file with inline CSS and JavaScript, no network requests, and fictional data. Each screen is a `<section id>` that opens by URL hash, so a requirement can cite `mockup/index.html#<screen-id>`; screens show their empty, error, and loading states.

   The look comes from, in order: the product's existing UI in the repository; the `frontend-design` skill when the repository has no UI and the harness provides the skill (Claude Code with that plugin installed); otherwise the skill's built-in skeleton. `Kind:` is `new` for a capability's first dated folder and `change` after that, with `## Changes` listing what differs from `Previous:`. Revise the mockup in the conversation until you confirm it.

   ## From inputs to requirements

   `/gin:discuss` reads `description.md` and any `mockup/index.html` of each dated folder of the affected capabilities. It cites only confirmed folders and asks about the others, and it turns `## Open questions` into questions or listed assumptions. Each requirement taken from an input gets a `Source:` line:

   ```markdown
   ### REQ-ORDERS-007: Reject a past delivery date
   The system SHALL reject a delivery date before today.
   Source: `assets/2026-05-11/description.md`, `assets/2026-06-02/mockup/index.html#new-order`
   ```

   The rest of the SDD flow is unchanged: discuss also writes the [diagrams](sdd.md#diagrams), `specs archive` copies the `Source:` lines into the living `spec.md`, and `gin specs export <capability>` prints them in the SRS.

   ## Commands

   | Command | Writes |
   |---|---|
   | `/gin-ba:capture <cap> [--date D] [paths]` | `assets/<D>/description.md` with `Kind: legacy` |
   | `/gin-ba:mockup <cap> [--date D]` | `assets/<D>/mockup/index.html` and `assets/<D>/description.md` |
   ````
