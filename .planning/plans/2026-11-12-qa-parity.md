# Plan: Legacy parity testing

Spec: .planning/specs/2026-11-12-qa-parity-design.md
Epic: gin-workflow-qa-parity
Workflow: gin-workflow-qa-parity

## Objective

`gin specs assets list` reports the dated asset folders of a capability; gin-qa cases carry a hash-neutral `Legacy:` reference; `/gin-qa:cases` writes cases from confirmed legacy captures; the brownfield starter names the tester as the one parity owner and the build parity runs against.

**Goal** (spec): parity tests have one owner, a case field for the legacy reference, and a stated build to run against.

**Architecture**: two independent code changes and one docs change. gin-workflow adds a read-only `assets list` beside `assets add`/`confirm` in `workflow_core/specs_assets.py`, reusing `_capability`, `_dated`, and `confirmed_date`. gin-qa adds `Legacy` to `KNOWN_FIELDS` with a validator and an export key, following `Moved from e2e`. The cases skill calls the new command by subprocess (gin-qa imports nothing from gin-workflow).

**Tech Stack**: Python 3 standard library; unittest/pytest (`tests/workflow_core/test_specs_assets.py`, `tests/gin_qa/test_cases_cli.py`); Markdown docs and skills.

**Global Constraints** (spec, verbatim):
- Out of scope: the SDD capture step in the starter (`gin-workflow-sdd-team-flow`, shipped); a command that records legacy payloads; accepting payload files in `gin specs assets add --legacy`.
- `Legacy:` was a free field before; a case that already used it keeps parsing, but its `hash8` changes once, so its test shows `stale` until `gin-qa tests pin` or `gin-qa e2e` re-pins it.
- `gin-qa cases export` only gains a key; gin-console does not read it.
- gin-qa keeps importing nothing from gin-workflow: the skill calls `gin specs assets list` by command.
- Assets exist only with the SDD layout; with the legacy layout the command lists nothing.

## Requirement Analysis
- Problem statement: parity has two owners and no build in the starter, cases cannot point at the legacy behaviour they check, and `/gin-qa:cases` ignores the BA's confirmed captures.
- Success criteria: spec requirements 1–6 and US-1 to US-3; `python3 -m pytest -n auto` passes.
- Constraints: Global Constraints above.
- Non-goals: recording payloads; payloads in asset folders.

## Approach Options
### Option 1: `assets list` command, known `Legacy:` field, payloads in the QA home (selected in `/discuss`)
- Summary: as the spec.
- Pros: one source for folder state (kind, confirmed) shared with `assets add`/`confirm`; hash stays stable on reference edits.
- Cons: a new subcommand and its docs.

### Option 2: the skill globs `description.md` files; `Legacy:` as a free field
- Summary: no core code.
- Pros: smaller diff.
- Cons: the skill must know the specs folder and workspace root; editing a reference makes tests stale; rejected in `/discuss`.

### Recommended Approach
- Selected option: Option 1 (confirmed in `/discuss` on 2026-11-12).
- Rationale: reuses the asset helpers and the `Moved from e2e` pattern.

## Scope
- In scope: spec requirements 1–6.
- Out of scope: see Global Constraints.
