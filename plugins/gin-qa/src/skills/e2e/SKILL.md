# E2E Specs

`/gin-qa:e2e <capability>` or `/gin-qa:e2e <TC-ID>...`, optionally `--parallel N` (default 3). All commands are `gin-qa e2e <command>`; exit 1 means findings to fix, exit 2 means wrong usage or a missing tool.

1. Preconditions: `gin` and `gin-qa` are on `PATH` and `.agent-workflow/generated/effective-config.yaml` exists; otherwise stop and name what to install or run (`install.sh --plugin gin-qa`, `/setup`). If `<e2e>/evidence.ts` is missing or the Playwright project (the e2e folder, or the root of an existing root setup) has no `playwright.config.*`, run `init --install` (it installs Playwright and chromium and adds the `e2e` script) and show its output. Without `--install`, `init` names those steps instead. When the config is missing, first ask the user once for the application URL and pass it as `init --base-url <url>`. `init` writes a config that finds specs under the e2e folder and falls back to that URL when `E2E_BASE_URL` is unset. If `<e2e>/evidence.ts` exists but does not contain `ariaSnapshot`, it predates step snapshots. Run `init`, which merges them when the fixture matches the template. If it says to merge by hand, stop and ask the user to merge the snapshot block quoted in [explore-case.md](references/explore-case.md). When a Playwright config exists and sets `baseURL`, do not ask for the URL. Ask for it, and for how to start the application, only when an existing config sets no `baseURL`.
2. `plan <capability> --format json` gives `e2e` (the folder), `guidelines` (a file), and the work: `missing`, `stale`, `orphan`. With TC-IDs, run `plan` and keep only those cases.
3. Read the guidelines file (`/gin-qa:cases` creates it). Its rules (locators, sign-in, test data) override everything below.
4. Note `git status --porcelain`. `missing` and `stale`: each case is built and checked against the running application by the procedure in [explore-case.md](references/explore-case.md), which ends with `done`, `app_defect`, or `blocked`.
   - When the platform has subagents, give each case to `gin-qa:e2e-tester` at the middle model and `low` effort, at most N at a time. Send it the `plan` row, the guidelines path, and the path of `explore-case.md`; nothing else from this conversation. Otherwise work through the cases one by one yourself.
   - A failed or blocked case does not stop the others.
5. When every case has ended, compare `git status --porcelain` with step 4: only these cases' spec files, and the `Result`, `Run`, and `Bug` lines of their case files, may have changed. Report any other change and ask the user before reverting it.
6. `orphan`: list the specs and ask the user whether to delete or keep each one. Never delete on your own.
7. Rerun step 2 with the same scope: every case that ended `done` or `app_defect` must be out of `missing` and `stale`; fix and repeat until it is. A `blocked` case keeps its draft spec and is reported, not retried. Then `run` the specs of the `done` and `app_defect` cases in one run: that folder is the official evidence, and the run records each case's result in its case file. Report the specs added and changed, the run folder with the results it recorded, each case's outcome (an `app_defect` names the step, its error, and the screenshot and snapshot paths; a `blocked` case its reason), and any `check` findings outside the scope without fixing them. Exploration runs stay in the git-ignored evidence root.
8. Bugs: list the `app_defect` cases and ask the user which ones to file. For each chosen case, ask for an external tracker reference as `/gin-qa:run` does (required when `## Bugs` in the guidelines says so), then run `gin-qa cases bug <TC-ID> --actual "<step>: <error>" --evidence "<screenshot>" [--external-ref "<ref>"] --run "<run folder>" --format json`. On exit 2 for the epic, offer the epics it lists, or `gin task list --type epic --json`, and run it again with `--discovered-from <bead>`. Report each bug as `<TC-ID> <bug>`, filed or kept open. Never file a bug the user did not choose.
9. A case that keeps failing or flaking on the pipeline can leave automation: when the user decides so, run `gin-qa cases to-manual <TC-ID> --reason <why>`. It renames the case to `.manual.md`, deletes the spec, and resets the result; `/gin-qa:run` then walks it.
10. Do not commit; the user reviews and commits.

Reports and other formats: `export --run <folder> --format json` joins every e2e case with its `results` (one per Playwright project) and their screenshot and snapshot paths; build them from that.
