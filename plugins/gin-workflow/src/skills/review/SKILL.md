## Before you start
1. If `.agent-workflow/generated/effective-config.yaml` does not exist in the main checkout (the parent of `git rev-parse --path-format=absolute --git-common-dir`; linked worktrees have none), stop: tell the user to run `/setup` once and do nothing else. (`capabilities: {}` is a valid config.)
2. Read [references/stage-contract.md](../../references/stage-contract.md) now: it defines the gate CLI, valid evidence, approval, and git rules this stage relies on.

# Review

Review after every track, after a major feature, and before merge; never skip because "it's simple". A completed implementation starts review; it is not evidence that the task may close. Ledgers live in `.planning/reviews/<bead-id>/` (legacy fallback `.planning/<bead-id>/`). All commands are `python3 review-ledger.py <cmd> --bead-id <bead-id> ...`; never hand-write or copy `review.json`.

## Requesting (implementer)
1. `init --repo-id <id> [--repo-path <worktree>] [--include <scope>] --max-cycles <project.max_cycles from state --format json>` once (idempotent), then `checkpoint --repo-id <id> --commit-msg "<msg>" --actor-id <id>` to snapshot the reviewed tree, then `gin evidence run` in the worktree (fix any failure first), then `transition-requested --to review-requested --actor-role worker --actor-id <id>`; without it the reviewer cannot approve. After `changes-requested`: fix, `transition-requested --to implementation-in-progress`, checkpoint, and request review again.
2. Pick the reviewer with `gin reviewer --base <ledger base> --implementer <provider> --model <model> [--effort <effort>] --json`. Spawn `gin:code-reviewer` with its `actor_id` (the reviewer uses the implementer's final model and effort, which includes any escalation, and never a lower one): natively when `route.provider == main_harness` supports it (`claude` `Agent`, or `antigravity` `invoke_subagent` at `provider_default`), else via `gin-orchestrator dispatch --workflow-id <id> --task-id <id> --role review --provider <provider> --model <model> [--effort <effort>] --stage review --agent code-reviewer --workspace <worktree> --objective "<review brief>" --json` (fallback: native subagent), trying the next on quota, rate-limit, or timeout failure (exit 2 means `human_decision_required`). Without a native subagent or `gin-orchestrator`, notify (`needs_input`) and stop for the user; no self-review unless `allow_self_review_fallback`. Give fresh context: reviewed diff, requirement, criteria, test evidence, rules checklist (`gin rules --files <reviewed files>`). Exclude private reasoning, self-assessment, persuasive summaries, unrelated history, secrets. Fixes after `changes-requested` go to `gin:developer` at its current route.
3. Record the implementation's original provider/model route as runtime affinity only; never put concrete providers in the plan or Beads.
4. Handle findings with the `review-response` skill: fix Critical immediately and Important before proceeding, note Minor ones, and push back with evidence when the reviewer is wrong.

## Reviewing (reviewer)
1. Independence follows `project.independence` from `gin state --format json`: `provider` — the reviewer provider must differ from the implementation provider; `session` — a fresh session/subagent of the same provider with a clean context and a different actor id (`reviewer:<provider>:session-<id>`), never the implementer's session. Self-review only under the explicit `allow_self_review_fallback` policy; otherwise route exhaustion needs a human decision. Provider independence needs gin-orchestrator; without it independence is `session`.
2. `start-review --actor-id <reviewer>` acquires the lease; the ledger refuses the init actor as reviewer (`--force-takeover --reason "<why>"` only when authorized; `resync-lease --lease-id <id>` after a stale revision). `validate` replays the ledger.
3. Inspect in-scope files for correctness, edge cases, error handling, security, performance, plan alignment; run tests in isolation unless `gin evidence check` in the worktree exits 0; then cite its record instead. Never modify implementation files. Check rules checklist, `critical`/`high` first; cite `<pack>#<anchor>`, record `critical` as `IMPORTANT`+. Grade `lean` by impact: `high` bullet as `IMPORTANT`, others `MINOR`; name cuts and replacements (ignore `simplified:`). Check docs claims against the code and grade docs findings per [references/docs-style.md](../../references/docs-style.md). With `project.layout: sdd`, each REQ scenario needs a test (the `sdd` skill).
4. Check each spec/plan requirement this track delivers against the code, not only the diff. Record each issue with `add-finding --finding-id <id> --severity <sev> --actor-id <reviewer> --lease-id <lease>`.
5. For a claimed fix, check the tree. If confirmed, `verify-finding`; if absent, incomplete, or wrong, `reopen-finding --reason "<why>"`. `verified` is terminal, so never verify what you could not confirm. If sources changed, re-run `checkpoint` before approving.
6. When every finding is terminal, `approve --actor-id <reviewer> --lease-id <lease>`; otherwise request changes with `transition-requested --to changes-requested --actor-role reviewer --actor-id <reviewer> --lease-id <lease>` (`reject` only invalidates an existing approval). Then `render`, and `release-lease --actor-id <reviewer> --lease-id <lease>` so the implementer can write again.
7. Write each ledger command with literal flags, never in shell variables (zsh does not split them); check its exit code and report only what its output shows. Run tests in the foreground with a timeout, and never stop a process you did not start.

## Cycles
Each unresolved revision is a new review cycle. `start-review` exits 1 at the maximum review cycles (`routing.review.max_cycles`, passed as `init --max-cycles`) with `max review cycles (N) reached`; return `human_decision_required` instead of retrying. Never loop unbounded. Never manufacture approval or close work on a notification.
