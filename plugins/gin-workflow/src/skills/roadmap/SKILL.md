# Roadmap

On `/roadmap` only. Outside the lifecycle: it records no gate. One question per message. Never write the roadmap file or touch Beads before the PM explicitly confirms the roadmap.

## Before you start
1. If `.agent-workflow/generated/effective-config.yaml` does not exist in the main checkout (the parent of `git rev-parse --path-format=absolute --git-common-dir`), stop: tell the user to run `/setup` once and do nothing else.
2. `gin state --format json` gives `project.stage` and `project.layout`. The roadmap file is `.planning/roadmap.md`, or `docs/roadmap.md` with `project.layout: sdd`.
3. `brownfield` or `legacy` prefers the tech-doc folder (`.planning/codebase/`, or `artifacts.codebase`, default `docs/codebase/`, with the SDD layout). If the folder is missing, recommend `/tech-doc` once in one sentence, then ask for a product brief (a path or the text). `greenfield` needs a product brief: ask for a path or the text.

## With --milestone <id>
1. Before anything else run `gin milestone show <id> --json`. A non-zero exit or `status: closed` stops the skill: report the message. In team mode, also stop when `project.team.permissions.milestone` in `gin state --format json` lists roles and none is in `project.team.me.roles`; name the roles. `project.team.me` is null when the git user is not a member, so the check stops. `permissions` is absent when team mode is off, so no check applies.
2. In step 4, propose `Estimate: <working days>` for every epic of the milestone, from the measured pace and the AI capacity. Find the closed `roadmap` epics with `gin task list --label roadmap --type epic --status closed --json`. Measure each from the `timestamp` of its earliest `requirement.confirmed` event (`workflow_id` is the epic) in `.agent-workflow/runtime/events.jsonl` of the main checkout to its `closed_at`. Without that event, start from the earliest `created_at` of its tracks (`gin task list --parent <epic> --all --json`); skip an epic with neither. Round each span up to whole working days, at least 1. When that list has no epic (no measured pace), ask the PM for one day value per size, small, medium and large, assign one size per epic, and mark each resulting `Estimate:` line `(assumed)` in the roadmap file. Otherwise never ask the PM for estimates; neither that size question nor an estimate revision counts against `project.max_questions`. Revise them on request. Also ask the sprint's lanes (streams of work that each run one epic at a time), default the number that starts the `AI capacity:` line; step 6 writes a different value with `gin milestone update <id> --lanes <n>`. Bound adoption by the scarcest role group or the lanes, per the Load block of [way of working](references/way-of-working.md).
3. Adoption: take the beads of `gin task list --label roadmap --type epic --limit 0 --json` with status `open` or `in_progress` and no `parent`. Propose which join the milestone, each with an estimate (the remaining working days for `in_progress`). The PM may add or drop epics and change estimates. Propose by dependency layer: epics with no open blocker first; an epic with an open blocker only when that blocker is proposed too; stop when the sum of estimates reaches the bound of step 2 (member count of the scarcest role group, or lanes) times the working days (Monday to Friday) between `start` and `end` of `gin milestone show <id> --json`. Name the epics left out and why (blocked, or over capacity). Never propose a closed epic. Never change an adopted epic's title, description, or dependencies.
4. In step 5, the file groups epics under `## Milestone: <title>`, opened by `Spec ready by:` and the `Integration point:` block of the reference's Milestone block, with `Milestone: <id>` and `Estimate: <days>` per epic. Name each adopted epic whose `spec_confirmed` is false in `gin milestone show <id> --json`. Epics without a milestone go under `## Unassigned`. A file without these lines is still valid input.
5. In step 6, after the sync (and after the roadmap PR merges when `team.approvals.roadmap` lists roles), set membership with `gin milestone move <epic>... --to <id>` and estimates with `gin milestone estimate <epic> <days>`. Set the lanes with `gin milestone update <id> --lanes <n>` when they differ from `lanes` in `gin milestone show <id> --json`. Set them no other way. When a `gin milestone move` or `estimate` call exits non-zero, stop and report its message and which epics were already set. The messages are: a denied role (exit 2) naming the roles; `pull failed, nothing written`; `moved <epics>; <epic> failed: ...` for a partial move; and `<change> written locally but not pushed`. A re-run continues, and Beads wins.
6. On a re-run, Beads wins for membership and estimates. Compare `gin milestone show <id> --json` with the file and report each difference (for example "E1 estimate: file 5, Beads 8") without writing Beads.

## Steps
1. **Read** every file of the tech-doc folder, subsystem subfolders included, yourself (no subagent summaries: epic dependencies come from reading across files), or the product brief; then living specs (or `.planning/specs/`), the roadmap file if it exists, and `gin task list --label roadmap --type epic --all --json` (Beads copies a parent's labels to its children, so tracks also carry `roadmap`; `--type epic` keeps them out). With `.codegraph/`, check load-bearing claims with `codegraph explore`.
2. **Clarify** with the PM (at most `project.max_questions` questions (`gin state --format json`, default 8); at the cap, say the scope is too large or unclear and propose splitting it into smaller epics, or list the rest as assumptions): business goals, deadline, fixed constraints (downtime, data migration), non-goals, cutover. Never ask the team composition: team mode reads `team.members`, otherwise the lanes apply. Always ask about AI capacity: whether the team builds with AI agents, how many AI accounts it has, and each member's quota. When the `AI capacity:` line in `## Constraints` of the roadmap file already holds it, show that line and ask the PM to confirm or correct it instead. Step 5 writes the answer on that line. Also ask for the project deadline (a date, or none); when `## Constraints` has a `Deadline:` line, show it for confirmation instead. Step 5 writes `- Deadline: YYYY-MM-DD` (or leaves it empty) and starts `AI capacity:` with the number of lanes; `gin milestone list` reads both. Do not number questions against the cap (no `2/8`): it is a ceiling, not a target; ask only what changes the roadmap.
3. **Propose 2–3 ways to split the work** (for example by bounded context, by risk, by business value) with trade-offs, sequenced by spec readiness and by real API or data needs only, with minimal dependencies and the foundation epics first when the project lacks CI/CD, environments, auth, flags, shell, or a contract convention; lead with your recommendation. Then propose the way of working from [way of working](references/way-of-working.md), tailored to the team and the tech-doc set, and revise until the PM confirms; on a re-run keep the confirmed `## Way of working` unless the PM asks for a change.
4. **Present the roadmap**. Each epic: title, `Epic: <id>`, `Goal:`, `Scope:`, `Out of scope:`, `Capabilities:` (with `project.layout: sdd`: the capabilities its requirements go to, as `[a-z][a-z0-9-]*` names taken from `docs/specs/README.md`, else from the Feature Catalog of `02-FEATURES.md`, else from the brief; a name without a folder under `artifacts.specs` is marked `(new)`; omitted with the legacy layout), `Depends on:` (epic ids), `Evidence:` (tech-doc file and section, or the brief), `Risks:`, `Complexity:` (`low`, `medium`, or `high` and the main driver in a few words: cross-module reach, unknown legacy behaviour, data migration, integration count). Every run proposes `Estimate: <working days>` per epic by the method of `--milestone` step 2. A new id (one not yet in the roadmap file) is `<prefix>-<slug>` (`gin task config get issue_prefix`; slug of lowercase letters, digits, and hyphens) and never changes once written; when `gin task show <id>` finds a bead, choose another slug. Check that dependencies are acyclic. On a re-run, present only what differs from the file and Beads. Revise until the PM explicitly confirms.
5. **Write** the file from `gin specs template roadmap.md` on branch `roadmap/<topic>` and commit. A plain `/roadmap` omits the milestone heading and the `Milestone:` lines, keeps `Estimate:`, and puts its epics under `## Unassigned`. Step 5 writes the confirmed way of working under `## Way of working`. When `team.approvals.roadmap` in `.agent-workflow/config.yaml` lists roles: push, ask approval, open the pull request, and return `awaiting_roadmap_review`. On the next run, take the PR URL from the PM or `gh pr list --head roadmap/<topic>`, then `gin team check <pr-url> --gate roadmap`: exit 0 continues with the merged file on the base branch; exit 1 shows the reasons and stops. Never work around a rejection.
6. **Sync Beads** for each epic in the file, after `gin task show <id> --json` (only an explicit not-found result means missing; any other failure stops the sync):
   - missing: `gin task create --id <id> --type epic --labels roadmap -d "<description>" "<title>"`;
   - existing, an epic labelled `roadmap`: `gin task update <id> --title "<title>" -d "<description>"`. Never `gin task create --id` an existing id: it replaces the bead and erases its description;
   - existing without the `roadmap` label or not an epic: an id collision; stop and report it, never update that bead;
   - the description comes from `gin specs template epic.md`, `Capabilities:` and `Complexity:` copied from the file;
   - dependencies: `gin task dep add <epic> <dependency>` for each `Depends on:` id; `gin task dep remove <epic> <dependency>` for a dependency on a `roadmap`-labelled epic that the file no longer lists (`gin task dep list <epic> --json`);
   - an epic that is `in_progress` or closed, or `open` and adopted into a milestone (in Beads, or in the confirmed roadmap: `milestone move` runs after this sync): warn and leave its title, description, and dependencies unchanged; when it is not closed and its title, description, or `Depends on:` list differs from the file, also run `gin task comment <epic> "[gin roadmap] <roadmap path> now says: <one line per difference: title, description, dependencies added or removed>. Bead left unchanged; the next /discuss <epic> reads this comment."`, unless the epic's most recent `[gin roadmap]` comment (`gin task comments <epic> --json`) has the same text; a closed epic gets no comment; a failed comment is reported and the sync continues; with the markdown task backend there are no comments: say so in one sentence;
   - estimates: `gin milestone estimate <epic> <days>` for an epic whose `estimated_minutes` in Beads is empty, or whose value the PM changed in this run; otherwise Beads wins and a differing `Estimate:` line is reported ("E1 estimate: file 5, Beads 8"), not written;
   - an epic labelled `roadmap` that the file no longer lists: report it and ask; never close or delete an epic;
   - a failing `gin task` call: stop and report which epics were synced; a re-run continues from there.
7. **Report**: the roadmap path, epics created and updated, dependency changes, epics that received a `[gin roadmap]` comment, `gin task ready` epics, the forecast from `gin milestone list --json` (`forecast`: finish, deadline, spare or overflow working days, unestimated count; overflow is reported, never blocks), the `spec_not_ready` warnings of `gin milestone show` when the milestone has a kickoff, the next step `/discuss <epic-id>`, and `gin setup refresh` to update the links in `AGENTS.md`.
